Cloud Fundamentals

Regions/AZs, the shared responsibility model, IAM, pricing models, and well-architected basics.

6 questions in this section

Explain Regions, Availability Zones, and Edge Locations

Easy⭐ VIfundamentals▼

📌 Revision keywords

  • Region = geo area
  • AZ = isolated DC
  • Edge = CDN PoP

Region — a geographic area (e.g. ap-south-1 Mumbai). Pick by latency to users, data-residency laws, and service availability.

Availability Zone (AZ) — one or more isolated data centers within a region, with independent power/network. Deploy across ≥2 AZs for high availability.

Edge Location — CloudFront/Route 53 points of presence close to users for caching/low-latency.

Interview tip

The key design rule: spread across multiple AZs to survive a data-center failure; spread across multiple Regions only for disaster recovery or global low-latency (more complex/costly).

What is the AWS Shared Responsibility Model?

Easyfundamentals▼

📌 Revision keywords

  • AWS: security OF the cloud
  • You: security IN the cloud

AWS secures the infrastructure — hardware, the global network, the hypervisor, managed-service internals ("security of the cloud").

You secure what you put in it — IAM permissions, OS patching (on EC2), security groups, encryption, application code, and your data ("security in the cloud").

The line shifts with the service: on EC2 you patch the OS; on Lambda/RDS AWS handles more. A common interview probe: "who patches the DB?" → on RDS, AWS does the engine; you still manage users/queries/access.

Explain IAM: users, roles, policies, and roles vs keys

Medium⭐ VIfundamentals▼

📌 Revision keywords

  • user/group/role
  • policy = JSON perms
  • roles > static keys
  • User — a person/long-lived identity; Group — a set of users sharing policies.
  • Role — an identity that's assumed temporarily; the right way for apps/EC2/Lambda to get permissions (issues short-lived credentials).
  • Policy — JSON of Effect/Action/Resource/Condition attached to identities or resources.

Best practice: apps should use an IAM role (e.g. an EC2 instance profile or ECS task role), never hard-coded access keys. Follow least privilege. For a Java app, the AWS SDK picks up role credentials automatically via the default credential chain — no secrets in code.

Identity-based vs resource-based policies; how is access evaluated?

Hardfundamentals▼

📌 Revision keywords

  • explicit deny wins
  • default deny
  • resource policy (S3 bucket)
  • Identity-based — attached to a user/role (what this identity can do).
  • Resource-based — attached to a resource (e.g. S3 bucket policy, SQS queue policy) controlling who can access it, including cross-account.

Evaluation logic

Default is deny. An action is allowed only if some policy explicitly allows it AND nothing explicitly denies it. Explicit deny always wins. Add SCPs (org guardrails) and permission boundaries on top. This "deny by default, explicit deny overrides" rule is a frequent interview question.

EC2 pricing models (On-Demand, Reserved, Spot, Savings Plans)?

Mediumfundamentals▼

📌 Revision keywords

  • On-Demand = flexible
  • Reserved/Savings = commit, cheaper
  • Spot = cheap, interruptible
  • On-Demand — pay per second/hour, no commitment; for unpredictable/short workloads.
  • Reserved Instances / Savings Plans — commit 1–3 yrs for up to ~72% off; for steady baseline load.
  • Spot — spare capacity up to ~90% off, but can be reclaimed with a 2-min warning; for fault-tolerant/batch work.

Typical strategy: Reserved/Savings for the baseline, On-Demand for spikes, Spot for stateless batch/CI. Cost-optimization questions love this trade-off.

What are the Well-Architected Framework pillars?

Mediumfundamentals▼

📌 Revision keywords

  • Ops, Security, Reliability
  • Perf, Cost, Sustainability

Six pillars: Operational Excellence, Security, Reliability, Performance Efficiency, Cost Optimization, and Sustainability.

You don't need to memorize all six perfectly, but referencing them shows maturity. In design rounds, frame decisions as trade-offs across reliability (multi-AZ), cost (right-sizing/Spot), and security (least privilege, encryption).

Compute

EC2, Auto Scaling, load balancers, containers (ECS/EKS/Fargate), and serverless (Lambda).

8 questions in this section

What is EC2 and what are instance types/AMIs?

Easycompute▼

📌 Revision keywords

  • virtual server
  • AMI = image
  • instance families

EC2 = resizable virtual servers. An AMI (Amazon Machine Image) is the template (OS + preinstalled software) used to launch instances.

Instance families target workloads: t (burstable/cheap), m (general), c (compute-heavy), r/x (memory-heavy), g/p (GPU). For a typical Spring Boot service, an m or c family is common. You pick based on CPU/memory profile and right-size using CloudWatch metrics.

How does Auto Scaling work (ASG, scaling policies)?

Medium⭐ VIcompute▼

📌 Revision keywords

  • min/desired/max
  • target tracking
  • health checks

An Auto Scaling Group keeps a fleet between min and max, aiming for desired capacity, across multiple AZs.

  • Target tracking — keep a metric at a target (e.g. CPU ~60%); simplest and most common.
  • Step / scheduled — react to thresholds or known traffic patterns.
  • Unhealthy instances are replaced automatically (self-healing).

This gives elasticity + HA. Mention warm-up/cooldown to avoid flapping, and that scaling works best with stateless apps (offload session/state to Redis/DynamoDB).

ALB vs NLB vs CLB — when to use which?

Medium⭐ VIcompute▼

📌 Revision keywords

  • ALB = L7/HTTP
  • NLB = L4/TCP, fast
  • CLB = legacy
  • ALB (Application LB) — Layer 7. Path/host-based routing, HTTP/HTTPS, WebSockets, gRPC; ideal for microservices and container routing.
  • NLB (Network LB) — Layer 4 (TCP/UDP). Ultra-low latency, millions of connections, static IPs; for extreme performance or non-HTTP.
  • CLB — legacy, avoid for new work.

For a Spring Boot REST/microservice fleet, ALB is the default (host/path routing, TLS termination, health checks). NLB when you need raw TCP throughput or a fixed IP.

ECS vs EKS vs Fargate?

Medium⭐ VIcompute▼

📌 Revision keywords

  • ECS = AWS-native orchestrator
  • EKS = managed Kubernetes
  • Fargate = serverless containers
  • ECS — AWS's own container orchestrator; simpler, deeply integrated, less to learn.
  • EKS — managed Kubernetes; portable, huge ecosystem, but more operational complexity.
  • Fargate — a launch type (works with ECS or EKS) where AWS runs the containers serverlessly — no EC2 nodes to manage; you pay per vCPU/memory.

Rule of thumb: ECS+Fargate for simplicity and "just run my containers"; EKS when you need Kubernetes portability/standardization or already have k8s expertise. Fargate trades a bit of cost/control for zero node management.

What is Lambda and when would you use it?

Medium⭐ VIcompute▼

📌 Revision keywords

  • serverless, event-driven
  • pay per invocation
  • cold start, 15-min limit

Lambda runs code in response to events (S3 upload, SQS message, API Gateway request, schedule) with no servers to manage; you pay per invocation + duration, and it scales automatically.

Good fits / limits

  • Great for: event processing, glue/automation, lightweight APIs, cron jobs, fan-out.
  • Watch: cold starts (JVM is heavier — consider provisioned concurrency, GraalVM, or SnapStart), 15-min max runtime, /tmp limits, statelessness.

For long-running or steady high-throughput Java services, containers (ECS/EKS) are usually cheaper and avoid cold-start pain.

How do you choose between EC2, containers, and Lambda?

Hardcompute▼

📌 Revision keywords

  • control vs management
  • traffic pattern
  • cost at scale
  • Lambda — spiky/event-driven, low-to-moderate volume, want zero ops; beware cold starts & cost at very high constant load.
  • Containers (ECS/EKS) — steady microservices, need control over runtime, portability, long-lived connections; the sweet spot for most Spring Boot apps.
  • EC2 — need full OS control, special hardware (GPU), or licensing tied to the instance.

Decision drivers: traffic shape (spiky vs steady), operational burden you'll accept, latency/cold-start tolerance, and cost at expected scale. A strong answer names the trade-off, not just one tool.

How does an app on EC2/ECS get AWS credentials securely?

Mediumcompute▼

📌 Revision keywords

  • instance profile / task role
  • temporary creds via metadata
  • no static keys

Attach an IAM role — an instance profile for EC2 or a task role for ECS. AWS injects short-lived, auto-rotated credentials via the instance metadata service (IMDS), and the AWS SDK picks them up automatically through the default credential chain.

So your Java code does S3Client.create() with no keys anywhere. Never bake access keys into AMIs, env vars, or code — that's the most common security finding. Use IMDSv2 to prevent SSRF credential theft.

In ECS, what are a task definition, task, and service?

Mediumcompute▼

📌 Revision keywords

  • task def = blueprint
  • task = running instance
  • service = keeps N running
  • Task definition — the blueprint: image, CPU/memory, ports, env vars, IAM task role, log config (like a Compose/Pod spec).
  • Task — a running instantiation of that definition (one or more containers).
  • Service — keeps a desired number of tasks running, integrates with the ALB target group, and handles rolling deployments.

This mirrors Kubernetes Deployment/Pod concepts — useful to draw the analogy if the interviewer knows k8s.

Storage & Databases

S3, EBS vs EFS, RDS/Aurora, DynamoDB, ElastiCache — and how to pick.

8 questions in this section

What is S3 and what are its key properties?

Easy⭐ VIstorage▼

📌 Revision keywords

  • object storage
  • 11 9's durability
  • buckets + keys

S3 is object storage — store files ("objects") in buckets by key. It's virtually unlimited, highly durable (11 nines), and accessed over HTTPS APIs (not a mountable filesystem).

Common uses & features

  • Static assets, backups, data lake, logs, file uploads.
  • Storage classes (Standard, Infrequent Access, Glacier) + lifecycle rules to cut cost.
  • Versioning, server-side encryption (SSE-S3/KMS), presigned URLs for temporary direct upload/download.

For Java apps, generate presigned URLs so clients upload directly to S3 instead of streaming through your service.

S3 consistency and storage classes?

Mediumstorage▼

📌 Revision keywords

  • strong read-after-write
  • Standard/IA/Glacier
  • lifecycle policies

S3 now provides strong read-after-write consistency for all operations (an older interview "gotcha" was eventual consistency — that changed in 2020).

Storage classes trade cost vs access: Standard (hot), Standard-IA / One Zone-IA (infrequent), Glacier / Deep Archive (cold, retrieval delay), Intelligent-Tiering (auto-moves based on access). Use lifecycle rules to transition old objects to cheaper tiers or expire them — a classic cost-optimization lever.

EBS vs EFS vs S3 — what's the difference?

Mediumstorage▼

📌 Revision keywords

  • EBS = block, 1 instance
  • EFS = shared NFS
  • S3 = object/HTTP
  • EBS — block storage (a virtual disk) attached to a single EC2 instance in one AZ; for DB data dirs, OS volumes.
  • EFS — managed NFS file system shared across many instances/AZs; for shared files.
  • S3 — object storage over HTTP; for unstructured blobs, not a filesystem.

Quick test: need a disk for one server → EBS; need a shared mount across servers → EFS; storing files/assets accessed by API → S3.

What is RDS and what does Multi-AZ vs Read Replica give you?

Medium⭐ VIstorage▼

📌 Revision keywords

  • Multi-AZ = HA/failover
  • Read Replica = scale reads

RDS is managed relational DB (PostgreSQL, MySQL, etc.) — AWS handles backups, patching, and failover; you handle schema/queries.

  • Multi-AZ — a synchronous standby in another AZ for high availability; automatic failover. Not for scaling reads.
  • Read Replica — asynchronous copies to scale read traffic (and can be promoted). Can introduce replication lag.

Key distinction interviewers probe: Multi-AZ = availability; Read Replicas = read scalability. Point your app's read-only queries at replicas, writes at the primary.

What is Aurora and how does it differ from standard RDS?

Mediumstorage▼

📌 Revision keywords

  • MySQL/Postgres-compatible
  • distributed storage, 6 copies
  • fast failover

Aurora is AWS's cloud-native engine compatible with MySQL/PostgreSQL. It separates compute from a distributed storage layer that replicates 6 copies across 3 AZs, giving better performance, faster failover, and storage that auto-grows.

Extras: up to 15 low-lag read replicas, Aurora Serverless (auto-scaling capacity), global database for cross-region DR. Trade-off: costs more than vanilla RDS but stronger HA/scale. Use it when you want managed relational with high availability and read scale.

What is DynamoDB and when would you choose it over RDS?

Hard⭐ VIstorage▼

📌 Revision keywords

  • managed NoSQL key-value
  • partition key design
  • single-digit ms at scale

DynamoDB is a fully-managed NoSQL key-value/document store with single-digit-millisecond latency at massive scale, automatic partitioning, and no servers to manage.

Choose it when

  • You need predictable low latency at huge scale and simple access patterns (lookup by key).
  • You can design around the partition key (avoid hot partitions) and known query patterns.

Choose RDS for complex queries, joins, ad-hoc reporting, and strong relational integrity. Mention features: on-demand vs provisioned capacity, GSIs for alternate queries, DynamoDB Streams (CDC), and the trade-off of denormalizing for access patterns.

What is ElastiCache and how do you use it with a Java app?

Mediumstorage▼

📌 Revision keywords

  • managed Redis/Memcached
  • cache-aside
  • sessions, rate limiting

ElastiCache is managed Redis or Memcached. Common uses: cache-aside for hot DB reads, session store for stateless apps, rate limiting, distributed locks, leaderboards.

// cache-aside pattern
value = redis.get(key);
if (value == null) {        // miss
  value = db.load(key);
  redis.setex(key, ttl, value);
}

From Spring, use Spring Data Redis / @Cacheable. Watch for cache stampede (use TTL jitter/locks) and stale data (set sensible TTLs / invalidate on write). Redis adds persistence/replication; Memcached is simpler/multi-threaded.

How do you pick the right database for a workload on AWS?

Hardstorage▼

📌 Revision keywords

  • access patterns first
  • relational vs NoSQL
  • purpose-built

Start from access patterns and data shape, not the tech:

  • Relational, joins, transactions, reporting → RDS/Aurora.
  • Massive scale, simple key lookups, predictable latency → DynamoDB.
  • Sub-ms caching/sessions → ElastiCache (Redis).
  • Full-text search/log analytics → OpenSearch.
  • Analytics/warehouse → Redshift; blobs → S3.

AWS pushes "purpose-built databases" — pick per workload rather than forcing everything into one engine. Strong answers state the access pattern, then map it.

Messaging & Integration

SQS, SNS, Kinesis, EventBridge, and API Gateway — decoupling and event-driven patterns.

6 questions in this section

What is SQS and what are Standard vs FIFO queues?

Medium⭐ VImessaging▼

📌 Revision keywords

  • Standard = at-least-once, best-effort order
  • FIFO = ordered, exactly-once
  • visibility timeout, DLQ

SQS is a fully-managed message queue for decoupling producers and consumers.

  • Standard — nearly unlimited throughput, at-least-once delivery, best-effort ordering (duplicates possible → make consumers idempotent).
  • FIFO — strict ordering + exactly-once processing within a message group, lower throughput.

Key concepts: visibility timeout (message hidden while being processed), DLQ for poison messages after N failed receives, and long polling to reduce empty receives. SQS is pull-based (consumers poll).

What is SNS and what is the fan-out pattern?

Mediummessaging▼

📌 Revision keywords

  • pub/sub, push
  • topics → subscribers
  • SNS+SQS fan-out

SNS is pub/sub: publishers send to a topic, and it pushes to many subscribers (SQS queues, Lambda, HTTP, email/SMS).

Fan-out: publish once to an SNS topic that delivers to multiple SQS queues, so several services each get their own copy to process independently and at their own pace. This decouples one event from many consumers — a very common AWS event-driven pattern (vs SQS alone, which is one queue/one logical consumer group).

SQS vs Kinesis vs Kafka (MSK) — when to use each?

Hard⭐ VImessaging▼

📌 Revision keywords

  • SQS = queue, delete after read
  • Kinesis/Kafka = log, replayable
  • ordering, multiple consumers
  • SQS — a queue; each message consumed once then deleted. Best for task/work distribution and decoupling. No replay.
  • Kinesis — a managed streaming log (shards); ordered per shard, retained for a window, multiple consumers can replay. For real-time analytics/streaming.
  • MSK (Kafka) — managed Kafka; partitions, consumer groups, replay, rich ecosystem; for high-throughput event streaming and when you want Kafka specifically.

Mental model: SQS = "do this once"; Kinesis/Kafka = "an ordered, replayable event log many consumers read". If you need replay, ordering per key, and multiple independent consumers → streaming, not SQS.

What is EventBridge and how does it differ from SNS?

Mediummessaging▼

📌 Revision keywords

  • event bus
  • content-based routing rules
  • SaaS/AWS event sources

EventBridge is a serverless event bus that routes events to targets based on content-matching rules (filter on the event JSON), with schema registry and many built-in AWS/SaaS sources.

Vs SNS: SNS is simple, high-throughput pub/sub (subscribe to a topic). EventBridge adds rich filtering, routing to 20+ target types, scheduling, and event archiving/replay. Use SNS for straightforward fan-out; EventBridge for event-driven architectures needing smart routing and integrations.

What is API Gateway and what does it provide?

Mediummessaging▼

📌 Revision keywords

  • managed API front door
  • auth, throttling, caching
  • REST vs HTTP API

API Gateway is a managed front door for APIs — it handles routing, authentication/authorization (Cognito, IAM, Lambda authorizers), throttling/rate limiting, request/response transformation, caching, and metrics.

It commonly fronts Lambda (serverless APIs) or backend services (HTTP/VPC link). Note: for container microservices behind an ALB, an ALB is often enough; API Gateway shines for serverless and when you need its built-in auth/throttling/usage-plan features.

How do you ensure reliable, idempotent message processing on AWS?

Hard⭐ VImessaging▼

📌 Revision keywords

  • at-least-once → idempotent consumer
  • dedup store
  • DLQ + retries

SQS Standard / SNS are at-least-once, so duplicates and retries happen. Make consumers idempotent:

  • Use a business/message ID; track processed IDs in a store (DynamoDB conditional put, or a DB unique constraint) and skip duplicates.
  • Tune visibility timeout > processing time so a message isn't redelivered mid-work.
  • Configure a DLQ with a max-receive count for poison messages; alert on DLQ depth.
  • For producers, the transactional outbox pattern avoids "saved to DB but message lost".

This ties directly to your Kafka/outbox knowledge — the principles transfer across messaging systems.

Networking & Security

VPC, subnets, security groups vs NACLs, Route 53, CloudFront, KMS, and secrets.

7 questions in this section

What is a VPC, and explain public vs private subnets

Medium⭐ VInetworking▼

📌 Revision keywords

  • isolated virtual network
  • public = route to IGW
  • private + NAT for egress

A VPC is your private, isolated network in AWS, divided into subnets across AZs.

  • Public subnet — has a route to an Internet Gateway; for load balancers / bastions.
  • Private subnet — no direct inbound from internet; app servers and databases live here. Outbound internet (e.g. calling an API) goes via a NAT Gateway in a public subnet.

Standard pattern: ALB in public subnets → app/EC2/ECS in private subnets → RDS in private (DB) subnets. This layered isolation is a frequent design-round expectation.

What is Route 53 and what routing policies exist?

Easynetworking▼

📌 Revision keywords

  • managed DNS
  • latency/failover/weighted
  • health checks

Route 53 is AWS's managed DNS + domain registrar with health checks. Routing policies:

  • Simple — one record.
  • Weighted — split traffic by % (canary/blue-green).
  • Latency — send users to the lowest-latency region.
  • Failover — route to a standby if the primary's health check fails.
  • Geolocation — route by user location.

Combined with health checks, it enables multi-region failover and global low-latency routing.

What is CloudFront and why use a CDN?

Easynetworking▼

📌 Revision keywords

  • CDN, edge caching
  • lower latency, offload origin
  • TLS, WAF, DDoS

CloudFront is AWS's CDN — it caches content at edge locations near users, cutting latency and offloading the origin (S3/ALB).

Benefits: faster static/dynamic delivery, TLS termination at the edge, integration with WAF and Shield for security/DDoS protection, and origin-shielding to reduce load. Common setup: CloudFront in front of an S3 bucket (static site) or an ALB (dynamic app) with appropriate cache behaviors/TTLs.

How does encryption work on AWS (KMS, at-rest, in-transit)?

Mediumnetworking▼

📌 Revision keywords

  • KMS manages keys
  • envelope encryption
  • at-rest + in-transit (TLS)

KMS manages encryption keys (CMKs) and integrates with most services. At-rest: enable encryption on S3, EBS, RDS, DynamoDB — they use KMS via envelope encryption (a data key encrypts data; KMS encrypts the data key). In-transit: TLS everywhere (ALB/CloudFront certs via ACM).

KMS gives centralized key control, rotation, and CloudTrail audit of every key use — important for regulated/financial platforms. You rarely handle raw keys; services call KMS for you.

How do you manage secrets (Secrets Manager vs Parameter Store)?

Medium⭐ VInetworking▼

📌 Revision keywords

  • Secrets Manager = rotation
  • SSM Parameter Store = config
  • never hardcode
  • Secrets Manager — stores secrets (DB passwords, API keys) with built-in automatic rotation and KMS encryption; costs per secret.
  • SSM Parameter Store — config + secrets (SecureString); cheaper, no built-in rotation; good for general config.

Your Spring Boot app fetches DB creds at startup via the SDK (IAM-controlled), so no passwords in application.yml, env vars, or git. Rotation means leaked creds expire quickly. This directly answers the very common "how do you handle DB credentials securely?" question.

What are VPC endpoints and why use them?

Hardnetworking▼

📌 Revision keywords

  • private access to AWS services
  • no NAT/internet
  • Gateway vs Interface

VPC endpoints let resources in private subnets reach AWS services privately, without going over the internet/NAT.

  • Gateway endpoints — for S3 and DynamoDB (route-table entry, free).
  • Interface endpoints (PrivateLink) — an ENI in your subnet for most other services (SQS, Secrets Manager, etc.).

Benefits: improved security (traffic never leaves the AWS network), and lower NAT cost/egress. A good senior-level detail when discussing locked-down, private architectures.

DevOps & Observability

CloudWatch, CloudTrail, IaC (CloudFormation/CDK/Terraform), CI/CD, and deployment strategies.

6 questions in this section

What does CloudWatch provide (metrics, logs, alarms)?

Medium⭐ VIdevops▼

📌 Revision keywords

  • metrics + logs + alarms
  • dashboards
  • alarm → SNS/auto scaling
  • Metrics — CPU, memory, request counts, latency, queue depth, plus custom app metrics.
  • Logs — centralize app/container logs (CloudWatch Logs), query with Logs Insights.
  • Alarms — trigger on thresholds → notify via SNS or drive Auto Scaling.
  • Dashboards + EventBridge for scheduled/automation.

For a Spring Boot app, ship Actuator/Micrometer metrics to CloudWatch and set alarms on error rate, p99 latency, and SQS lag. Mention distributed tracing via X-Ray for request-level visibility.

CloudWatch vs CloudTrail — what's the difference?

Easydevops▼

📌 Revision keywords

  • CloudWatch = performance/health
  • CloudTrail = API audit log

CloudWatch = monitoring/observability — "how is my system performing?" (metrics, logs, alarms).

CloudTrail = governance/audit — "who did what in my account?" It records every API call (who, when, from where). Essential for security investigations and compliance.

One-liner: CloudWatch watches your app's behavior; CloudTrail watches actions on your AWS account.

Infrastructure as Code on AWS (CloudFormation/CDK/Terraform)?

Medium⭐ VIdevops▼

📌 Revision keywords

  • declarative, repeatable
  • CFN native, CDK code, TF multi-cloud
  • CloudFormation — AWS-native, declarative YAML/JSON templates; manages stacks.
  • CDK — define infra in real code (TypeScript/Java) that synthesizes to CloudFormation; great for developers.
  • Terraform — popular, multi-cloud, declarative HCL with state management.

Why IaC: version-controlled, repeatable, reviewable infra — no manual "click-ops" drift, easy to recreate environments. Mention that infra changes go through PRs/CI like app code. As a Java dev, CDK (with Java) lets you stay in one language.

How do you build a CI/CD pipeline to deploy to AWS?

Mediumdevops▼

📌 Revision keywords

  • build → image → ECR → deploy
  • CodePipeline / GitHub Actions

Typical container pipeline:

  1. Push to git → CI (GitHub Actions / Jenkins / CodeBuild) runs tests + builds the jar.
  2. Build a Docker image, push to ECR.
  3. Deploy: update the ECS service / EKS deployment / Lambda to the new image (CodeDeploy or aws ecs update-service).
  4. Run smoke tests / health checks; roll back on failure.

Use OIDC roles (not static keys) for the CI to assume AWS permissions. Mention environment promotion (dev→staging→prod) with approvals, and immutable image tags for traceability.

Blue-green vs canary vs rolling deployments on AWS?

Hard⭐ VIdevops▼

📌 Revision keywords

  • rolling = gradual replace
  • blue-green = swap envs
  • canary = small % first
  • Rolling — replace instances/tasks gradually (ECS default). Simple, no extra cost, but mixed versions briefly.
  • Blue-green — stand up a full new environment, then switch the ALB/Route 53 over; instant rollback by switching back. Costs double briefly.
  • Canary — send a small % of traffic to the new version, watch metrics, then ramp up (CodeDeploy/weighted target groups).

For zero-downtime, you also need backward-compatible DB migrations and graceful shutdown (drain connections on SIGTERM). Choose based on risk tolerance and cost — canary for high-risk changes, rolling for routine ones.

How do you control/optimize AWS costs?

Mediumdevops▼

📌 Revision keywords

  • right-size + auto scale
  • Savings Plans/Spot
  • S3 lifecycle, budgets/alerts
  • Right-size instances using CloudWatch; scale to zero/down off-peak with ASG schedules.
  • Savings Plans/Reserved for baseline, Spot for batch/stateless.
  • S3 lifecycle to cheaper tiers; delete unattached EBS/old snapshots/idle NAT.
  • Tagging for cost allocation; Budgets + alerts and Cost Explorer to catch surprises.
  • Serverless (Lambda/Fargate) to avoid paying for idle capacity on spiky workloads.

Frame it as continuous: measure (Cost Explorer), then right-size, commit, and clean up waste.
