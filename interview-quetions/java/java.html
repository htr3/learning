Why is Java called platform independent?

Easy⭐ VIcore▼

📌 Revision keywords

  • bytecode
  • JVM
  • JVM interprets or JIT

Source compiles to bytecode (.class), not CPU-specific machine code. Any OS with a JVM runs the same bytecode.

Flow

  1. Write .java
  2. javac → bytecode
  3. JVM interprets or JIT-compiles to native code

Nuance: Java is platform-independent; the JVM is platform-specific (install Windows/Linux JVM).

Interview line

"Write Once, Run Anywhere" — javac targets the JVM, not the OS. The trade-off is a warm-up cost (interpret → JIT) vs C/C++ native. Tools like GraalVM native-image AOT-compile to a native binary for fast startup (useful for serverless/containers) at the cost of some dynamic features.

JDK vs JRE vs JVM?

Easycore▼

📌 Revision keywords

  • JVM
  • JRE
  • JDK
  • JVM — runs bytecode
  • JRE — JVM + libraries (legacy term)
  • JDK — JRE + javac, javadoc, tools for development

You develop with JDK; production containers often need JRE/runtime only.

How they nest

JDK  ⊃  JRE  ⊃  JVM
(compiler+tools)  (libs+runtime)  (executes bytecode)

Note: since Java 11 Oracle no longer ships a standalone JRE — you ship a trimmed runtime via jlink or just use a JDK base image. In Docker, a JRE/`jlink` image keeps the container small.

== vs equals() — when to use which?

Easy⭐ VIcore▼

📌 Revision keywords

  • ==
  • equals()
  • references
  • content

Rule

== on objects compares references. equals() compares content when overridden.

Example

String a = new String("hi");
String b = new String("hi");
a == b;       // false
a.equals(b);  // true

String x = "hi";
String y = "hi";
x == y;       // true — string pool

Primitives

For int, boolean use == only.

Gotchas

  • If you override equals() you must override hashCode() too.
  • Use Objects.equals(a, b) for null-safe comparison.
  • equals on an enum is fine with == (single instances).

Interface vs abstract class?

Easycore▼

📌 Revision keywords

  • API

Interface

Contract; multiple inheritance; default/static methods (Java 8+). No state (until records/patterns evolve).

Abstract class

Shared fields + partial implementation; single inheritance.

Prefer interface for API boundaries between modules.

How to choose

  • Need multiple inheritance of type / a pure contract → interface.
  • Need shared state + partial implementation → abstract class.

Since Java 8 interfaces can have default/static methods, blurring the line — but interfaces still can't hold instance state or constructors.

Method overloading vs overriding?

Easycore▼

📌 Revision keywords

  • In simple terms:
  • trade-offs

Overloading

Same class, same method name, different parameters — compile-time polymorphism.

Overriding

Subclass replaces parent method — runtime polymorphism; use @Override.

Example

class ReportService {
  void export(String id) { }
  void export(String id, String format) { } // overload
}
class PdfReport extends ReportService {
  @Override void export(String id) { /* PDF */ }
}

Overriding rules

  • Same signature; return type can be covariant (subtype).
  • Can't reduce visibility; can't throw broader checked exceptions.
  • Resolved at runtime (dynamic dispatch); overloading is resolved at compile time by the static type.

Composition over inheritance?

Mediumcore▼

📌 Revision keywords

  • In simple terms:
  • Composition over inheritance
  • Instead of extending a fat base class, wrap/has-a collaborator.
  • Flexible, avoids fragile base class hierarchy.

Example

class OrderService {
  private final NotificationSender sender; // composed
  OrderService(NotificationSender sender) {
    this.sender = sender;
  }
}

Favor has-a over is-a when behavior stacks combine.

Why prefer composition

  • No fragile base class — parent changes don't ripple into subclasses.
  • Swap behavior at runtime (Strategy pattern).
  • Easier to test (inject a mock collaborator).

Rule of thumb: use inheritance only for a true "is-a" with a stable contract; otherwise "has-a".

Does Java pass by reference or value?

Medium⭐ VIcore▼

📌 Revision keywords

  • pass by value

Always pass by value — copy of reference for objects. You cannot swap two references from caller side.

Example

void swap(int[] a, int[] b) {
  int[] temp = a;
  a = b;  // only local copies change
  b = temp;
}

Mutating object state through reference affects caller; reassigning parameter does not.

The classic clarification

void f(StringBuilder sb) {
  sb.append("x");      // ✅ caller sees "x" (same object mutated)
  sb = new StringBuilder(); // ❌ caller unaffected (reassigning the copy)
}

So: object state changes are visible; re-pointing the parameter is not. Java is strictly pass-by-value (the value being a reference for objects).

How do you make a class immutable?

Medium⭐ VIcore▼

📌 Revision keywords

  • In simple terms:
  • how
  • final class, private final fields
  • No setters
  • Defensive copy of mutable inputs (List, Date)
  • Return copies from getters

Example

public final class Money {
  private final BigDecimal amount;
  public Money(BigDecimal amount) {
    this.amount = amount;
  }
  public BigDecimal getAmount() { return amount; }
}

Immutable objects are thread-safe — great for DTOs and cache keys.

Why it matters

  • Inherently thread-safe — no synchronization needed.
  • Safe as Map/Set keys (hashCode never changes).
  • Easy to reason about and cache.

Shortcut: a record gives you an immutable carrier for free (final fields, accessors, equals/hashCode).

String vs StringBuilder vs StringBuffer?

Easystring▼

📌 Revision keywords

  • String
  • StringBuilder
  • StringBuffer
  • String — immutable; every concat may create new object
  • StringBuilder — mutable, fast, not thread-safe
  • StringBuffer — synchronized legacy

Example

StringBuilder sb = new StringBuilder();
for (String row : rows) {
  sb.append(row).append(",");
}
String csv = sb.toString();

Use StringBuilder in loops building large text (report CSV export).

Extra detail

  • Pre-size with new StringBuilder(expectedLen) to avoid internal array resizes.
  • Simple a + b is fine — the compiler uses StringBuilder under the hood; the problem is concatenation in a loop.
  • StringBuffer is just the synchronized (slower) variant — rarely needed.

String pool and intern()?

Mediumstring▼

📌 Revision keywords

  • intern()

Literal strings live in pool; intern() returns pooled instance. Saves memory but pool is global — don't intern unbounded user input.

Example

String a = "report";
String b = "report";
a == b; // true — same pool entry

Extra detail

  • The pool lives in the heap (since Java 7), so it's GC-eligible.
  • Security: avoid storing passwords in String (it lingers in memory/pool) — use char[] you can wipe.
  • new String("x") always creates a new object; the literal "x" is pooled.

equals() and hashCode() contract?

Medium⭐ VIstring▼

📌 Revision keywords

  • HashMap

Rule

If a.equals(b) then a.hashCode() == b.hashCode(). Override both together for HashMap keys.

Example

@Override public boolean equals(Object o) {
  if (this == o) return true;
  if (!(o instanceof User u)) return false;
  return Objects.equals(email, u.email);
}
@Override public int hashCode() {
  return Objects.hash(email);
}

Broken contract → HashMap duplicates or lost keys.

The equals contract (5 rules)

Reflexive, symmetric, transitive, consistent, and x.equals(null)==false. Also: equal objects must have equal hashCodes (the reverse isn't required). Use your IDE/Lombok or Objects.equals/Objects.hash rather than hand-rolling.

  • finalize
  • GC
  • final — can't reassign variable; can't override method; can't extend class
  • finally — runs after try/catch (cleanup)
  • finalize — deprecated GC hook — don't use

Example

try (Connection conn = dataSource.getConnection()) {

Autoboxing and pitfalls?

Easystring▼

📌 Revision keywords

  • In simple terms:
  • Autoboxing and pitfalls
  • int ↔ Integer automatic.
  • Null Integer unboxed → NPE.
  • == on Integer outside -128..127 cache compares references.

Example

Integer a = 200, b = 200;
a == b; // false
Integer x = 100, y = 100;
x == y; // true — cached

Performance & safety

  • Boxing in tight loops creates garbage — prefer primitive streams (IntStream) / arrays on hot paths.
  • The Integer cache is -128..127 — that's why == "works" for small values and silently breaks above it.
  • Unboxing a null wrapper → NullPointerException.

What does the JVM JIT compiler do?

Mediumstring▼

📌 Revision keywords

  • JVM
  • Hot methods compiled to native code after profiling — faster than interpret.
  • Cold start after deploy slower until warm-up.

Vodafone/Optima: post-deploy smoke helps JIT + connection pool warm-up.

Tiered compilation

The JVM starts interpreting, then C1 (client) compiles quickly, then C2 (server) optimizes hot methods aggressively (inlining, escape analysis). This is why throughput improves after warm-up. Inspect with -XX:+PrintCompilation; a post-deploy smoke/load step warms the JIT and connection pool before real traffic.

ArrayList vs LinkedList?

Easycollections▼

📌 Revision keywords

  • ArrayList:
  • LinkedList:
  • ArrayList

ArrayList: dynamic array, O(1) get, amortized O(1) append end. LinkedList: O(n) get, O(1) insert at known node.

Default: ArrayList unless you need Deque operations at both ends.

Example

List reports = new ArrayList<>();
reports.add("R001");
String first = reports.get(0);

In practice

Almost always use ArrayList: cache-friendly contiguous memory and O(1) indexed access. LinkedList has high per-node overhead and poor locality; even queue/stack use cases are better served by ArrayDeque. Pre-size the ArrayList if you know the count.

HashMap internal working (Java 8+)?

Hard⭐ VIcollections▼

📌 Revision keywords

  • HashMap

Structure

Array of buckets; index = (n-1) & hash. Collision: linked list → red-black tree if chain > 8 and table ≥ 64.

put flow

  1. Compute hash
  2. Find bucket
  3. Same key (equals) → replace value
  4. Else add to chain/tree

Load factor

0.75 → resize double, rehash.

Why treeify & hash spreading

  • Chains convert to red-black trees (≥8 in a bucket, table ≥64) to bound worst-case lookup at O(log n) — a defense against hash-collision DoS.
  • HashMap spreads the hash (h ^ (h >>> 16)) so high bits influence the bucket index.
  • Mutating a key's hashCode after insertion "loses" the entry — keep keys immutable.

HashMap vs Hashtable vs ConcurrentHashMap?

Medium⭐ VIcollections▼

📌 Revision keywords

  • HashMap
  • Hashtable
  • ConcurrentHashMap
  • HashMap — not thread-safe, one null key
  • Hashtable — legacy synchronized — slow
  • ConcurrentHashMap — fine-grained locks/CAS — use for shared caches

Example

Map cache = new ConcurrentHashMap<>();
cache.put(id, report);

Extra detail

  • CHM allows no null keys or values (unlike HashMap) — a null would be ambiguous under concurrency.
  • Use atomic helpers: compute, merge, computeIfAbsent for safe read-modify-write.
  • Iteration is weakly consistent (no ConcurrentModificationException).

HashSet vs TreeSet?

Mediumcollections▼

📌 Revision keywords

  • HashSet:
  • TreeSet:

HashSet: O(1) add/contains, no order. TreeSet: Red-black tree, sorted, O(log n). Use TreeSet when you need range queries or sorted iteration.

Don't forget LinkedHashSet

LinkedHashSet keeps insertion order with near-HashSet speed. TreeSet needs elements to be Comparable (or a Comparator) and offers navigation (floor, ceiling, headSet) — pick it only when you need ordering/range queries.

HashMap of List — common pattern and pitfall?

Medium⭐ VIcollections▼

📌 Revision keywords

  • HashMap
  • ArrayList
  • Group records by key.
  • Pitfall: mutating list from getter without checking null.

Example

Map> byAccount = new HashMap<>();
byAccount.computeIfAbsent(accountId, k -> new ArrayList<>()).add(report);

computeIfAbsent is cleaner than get/put null checks.

Alternatives & concurrency

Comparable vs Comparator?

Mediumcollections▼

📌 Revision keywords

  • Comparable
  • Comparator

Comparable — natural order inside class (compareTo). Comparator — external, multiple sort orders.

Example

reports.sort(Comparator.comparing(Report::getCreatedAt).reversed());

Composing comparators

reports.sort(
  Comparator.comparing(Report::getStatus)
            .thenComparing(Report::getCreatedAt, Comparator.reverseOrder())
            .thenComparing(Report::getId, Comparator.nullsLast(naturalOrder())));

thenComparing, reversed, and nullsFirst/Last cover almost every real sorting need without writing a custom class.

fail-fast vs fail-safe iterators?

Hardcollections▼

📌 Revision keywords

  • ArrayList

fail-fast

ArrayList iterator throws ConcurrentModificationException if collection structurally modified during iteration (except iterator.remove).

fail-safe

CopyOnWriteArrayList iterates snapshot — safe under concurrent reads.

Example

for (String id : ids) {
  if (expired(id)) ids.remove(id); // throws on ArrayList
}
ids.removeIf(this::expired); // safe

Under the hood

Fail-fast iterators track a modCount; a structural change mid-iteration trips a ConcurrentModificationException — it's a best-effort bug detector, not a guarantee. To remove safely use iterator.remove() or removeIf(); for concurrent reads use CopyOnWriteArrayList/ConcurrentHashMap.

Queue and Deque in Java?

Easycollections▼

📌 Revision keywords

  • Queue:
  • Deque:
  • BFS

Queue: FIFO — LinkedList, PriorityQueue. Deque: double-ended — ArrayDeque for stack/queue. Used in BFS, task scheduling.

Two method families

  • Throwing: add/remove/element.
  • Returning special value: offer/poll/peek (return false/null instead of throwing).

ArrayDeque is the go-to stack/queue (faster than Stack/LinkedList). For concurrency use BlockingQueue / ConcurrentLinkedQueue.

Optional — when and when not?

Mediumcollections▼

📌 Revision keywords

  • In simple terms:
  • Optional — when and when not

Good

Return type when value may be absent — forces caller to handle.

Bad

Fields, method parameters, collections of Optionals.

Example

public Optional findById(String id) {
  return repo.findById(id);
}

orElse vs orElseGet

How do you make code thread-safe?

Hard⭐ VIconcurrency▼

📌 Revision keywords

  • Spring
  • Stateless Spring beans

Strategies

  • Immutability (best)
  • synchronized / ReentrantLock on critical sections
  • ConcurrentHashMap, AtomicLong
  • Stateless Spring beans — no mutable instance fields

Deadlock

Two locks opposite order → deadlock. Fix: consistent lock ordering, tryLock timeout.

The mental model

Thread-safety is really about visibility + atomicity under the Java Memory Model. Establish a happens-before edge (via synchronized, volatile, or concurrent classes). Cheapest strategies first: immutability and thread confinement (don't share), then lock-free atomics, then locks.

Thread pool / ExecutorService?

Medium⭐ VIconcurrency▼

📌 Revision keywords

  • Spring
  • Reuse threads instead of new Thread() per task.
  • Configure core/max pool and bounded queue.

Example

ExecutorService pool = Executors.newFixedThreadPool(8);
pool.submit(() -> generateReport(id));
// Spring @Async uses TaskExecutor — configure queue size

Unbounded queue + slow tasks → OOM.

Lifecycle & pool types

  • Always shutdown() then awaitTermination(); use shutdownNow() to interrupt.
  • newFixedThreadPool (bounded threads), newScheduledThreadPool (cron-like), virtual-thread executor (Java 21).
  • Avoid newCachedThreadPool in prod — unbounded thread growth.

Callable vs Runnable?

Mediumconcurrency▼

📌 Revision keywords

  • In simple terms:
  • trade-offs
  • Runnable no return value.
  • Callable returns result and throws checked exceptions — used with Future/ExecutorService.

What does volatile do?

Mediumconcurrency▼

📌 Revision keywords

  • In simple terms:
  • What does volatile do
  • Visibility across threads — reads see latest write.
  • Does NOT make compound actions atomic (i++ still needs sync or AtomicInteger).

Example

private volatile boolean shutdown = false;
// writer thread sets true; readers see immediately

Where it fits

  • Guarantees visibility + ordering (a happens-before edge), used for flags and the double-checked-locking singleton field.
  • Does not make i++ atomic — use AtomicInteger or a lock for read-modify-write.

Detect and prevent deadlock?

Hardconcurrency▼

📌 Revision keywords

  • In simple terms:
  • Detect and prevent deadlock

Example deadlock

Thread1: lock A then B. Thread2: lock B then A.

Prevention

  • Always acquire locks in same global order
  • tryLock with timeout
  • Reduce lock scope

Theory + tooling

Deadlock needs all four Coffman conditions (mutual exclusion, hold-and-wait, no preemption, circular wait) — break any one. Detect a live deadlock with a thread dump (jstack) — it prints "Found one Java-level deadlock". Prevent with global lock ordering and tryLock(timeout).

ThreadLocal use case?

Mediumconcurrency▼

📌 Revision keywords

  • In simple terms:
  • ThreadLocal use case
  • Per-thread variable — e.g.
  • SimpleDateFormat (legacy), user context, correlation ID in servlet thread.
  • Clear in finally to avoid leaks in thread pools.

Example

private static final ThreadLocal CORR = new ThreadLocal<>();
CORR.set(correlationId);
try { process(); } finally { CORR.remove(); }

The leak trap

In a thread pool, threads are reused, so a ThreadLocal you never remove() keeps its value (and can leak memory / leak data into the next request). Always clear in a finally. InheritableThreadLocal passes a value to child threads (but not to pool threads).

CompletableFuture for async composition?

Hardconcurrency▼

📌 Revision keywords

  • In simple terms:
  • CompletableFuture for async composition

Chain async steps without blocking threads — thenApply, thenCombine, exceptionally.

Example

CompletableFuture.supplyAsync(() -> fetchAccount(id))
  .thenApply(acc -> buildReport(acc))
  .exceptionally(ex -> Report.error(ex));

Composition toolkit

CompletableFuture.allOf(f1, f2).join();        // wait for all
a.thenCombine(b, (x, y) -> merge(x, y));        // combine two

Always supply your own executor for blocking work (the common ForkJoinPool is shared and small). Use exceptionally/handle for error paths.

Threading Deep Dive

Thread lifecycle, creation, locks, coordination, pools & virtual threads — high-scale multi-tenant focus.

12 questions in this section

What are the states in a thread's lifecycle?

Medium⭐ VIthreading▼

📌 Revision keywords

  • NEW
  • RUNNABLE
  • BLOCKED
  • WAITING
  • TERMINATED

The six states

  • NEW — created but start() not called.
  • RUNNABLE — running or ready to run (scheduler decides).
  • BLOCKED — waiting to acquire a monitor lock (entering a synchronized block).
  • WAITING — waiting indefinitely (wait(), join() with no timeout).
  • TIMED_WAITING — waiting with a timeout (sleep(), wait(ms)).
  • TERMINATED — finished or threw.

Nuance: Java has no separate "RUNNING" state — running and ready are both RUNNABLE.

How to inspect

A thread dump (jstack <pid>) shows each thread's state — lots of BLOCKED points at lock contention; many WAITING on the same monitor points at a coordination bug.

What are the ways to create a thread in Java?

Easy⭐ VIthreading▼

📌 Revision keywords

  • Runnable
  • Thread
  • Callable
  • ExecutorService

Options

  • Extend Thread and override run() — least flexible (uses up your single inheritance).
  • Implement Runnable — preferred; decouples task from thread.
  • Implement Callable — returns a value / throws; submit to executor.
  • Use an ExecutorService / thread pool — what you do in real apps.

Example

Runnable task = () -> process(id);
ExecutorService pool = Executors.newFixedThreadPool(4);
pool.submit(task);

In Spring, prefer @Async + a configured TaskExecutor over raw threads.

Why Runnable over Thread

Implementing Runnable/Callable separates the task from the execution mechanism, leaves your single inheritance slot free, and lets you hand the task to any executor (or a virtual-thread executor).

start() vs run() — what's the difference?

Easy⭐ VIthreading▼

📌 Revision keywords

  • start()
  • new thread
  • run() = same thread

Key point

  • start() → JVM creates a new call stack, invokes run() on the new thread.
  • run() → ordinary method call on the current thread; no concurrency.
  • Calling start() twice throws IllegalThreadStateException.

Interview trap

"What happens if I call run() directly?" → it runs synchronously on the current thread with no new stack — a common bug that looks like threading but isn't concurrent at all.

sleep() vs wait() — when to use which?

Medium⭐ VIthreading▼

📌 Revision keywords

  • sleep = Thread, keeps lock
  • wait = Object, releases lock

Comparison

  • sleep() — static on Thread; does NOT release locks; timed.
  • wait() — on Object; must hold the monitor; releases the lock; woken by notify()/notifyAll().
  • Both must handle/throw InterruptedException.

Always handle interruption

Both throw InterruptedException. On catch, either propagate it or restore the flag with Thread.currentThread().interrupt() — swallowing it silently breaks cancellation.

How do wait() / notify() / notifyAll() work?

Hard⭐ VIthreading▼

📌 Revision keywords

  • monitor
  • while loop guard
  • spurious wakeups

Rules

  • Must be called inside synchronized on the same object.
  • Always re-check the condition in a while loop (guards spurious wakeups).
  • Prefer notifyAll() unless you can prove one waiter suffices.

Example

synchronized (queue) {
  while (queue.isEmpty()) {
    queue.wait();          // releases lock, waits
  }
  return queue.poll();
}
// producer: synchronized(queue){ queue.add(x); queue.notifyAll(); }

Modern code: prefer BlockingQueue or Condition over raw wait/notify.

Why the while loop (not if)

Spurious wakeups and multiple waiters mean the condition can be false even after waking — re-checking in a while prevents acting on a stale condition (the "lost/early wakeup" bug).

synchronized vs ReentrantLock?

Hard⭐ VIthreading▼

📌 Revision keywords

  • tryLock
  • fairness
  • interruptible
  • Condition

synchronized

  • Built-in, auto-released on exit/exception; no timeout, no try-acquire.

ReentrantLock

  • tryLock(timeout), lockInterruptibly(), optional fairness, multiple Conditions.
  • Must unlock in finally or you leak the lock.

Example

lock.lock();
try { /* critical section */ }
finally { lock.unlock(); }

Other lock types

For read-heavy data use ReadWriteLock (many readers, one writer) or StampedLock (optimistic reads). Pick synchronized for simple mutual exclusion; reach for Lock when you need timeout/interruptible/fairness/conditions.

What does join() do?

Easythreading▼

📌 Revision keywords

  • wait for thread to finish

Use case

Coordinate completion — e.g. start several workers, then join() each before aggregating results. Supports an optional timeout.

worker.start();
worker.join();   // block until worker done
// continue with results

Notes

join(timeout) avoids waiting forever; it can throw InterruptedException. For many tasks, an ExecutorService + invokeAll/CompletableFuture.allOf is cleaner than manual joins.

What is a race condition? Show one and fix it.

Hard⭐ VIthreading▼

📌 Revision keywords

  • check-then-act
  • atomicity
  • CAS / lock

Broken

private int count = 0;
void inc() { count++; }   // read-modify-write, NOT atomic

Fixes

  • AtomicInteger.incrementAndGet() (CAS, lock-free).
  • synchronized method / block.
  • ConcurrentHashMap.compute() for map updates.

Two distinct hazards

Be precise in interviews: a visibility bug (one thread doesn't see another's write → fix with volatile) is different from an atomicity bug (interleaved read-modify-write → fix with atomics/locks). count++ has both.

Implement producer–consumer with a BlockingQueue.

Hard⭐ VIthreading▼

📌 Revision keywords

  • BlockingQueue
  • put/take
  • backpressure

Example

BlockingQueue q = new LinkedBlockingQueue<>(1000);
// producer
q.put(task);            // blocks if full → backpressure
// consumer
Task t = q.take();      // blocks if empty
process(t);

Bounded capacity prevents OOM under load — important for multi-tenant services.

Scaling & shutdown

Works with N producers and M consumers on one queue. For clean shutdown, send a poison pill (sentinel) per consumer, or interrupt and drain. The bounded capacity provides natural backpressure.

How do you size a thread pool?

Hard⭐ VIthreading▼

📌 Revision keywords

  • CPU-bound ≈ cores
  • IO-bound > cores
  • bounded queue

Rules of thumb

  • CPU-bound: ≈ number of cores (Runtime.availableProcessors()).
  • IO-bound: cores × (1 + wait/compute ratio) — can be much larger.
  • Always use a bounded queue + a rejection policy; unbounded queues hide overload and cause OOM.
new ThreadPoolExecutor(core, max, 60, SECONDS,
   new ArrayBlockingQueue<>(500),
   new ThreadPoolExecutor.CallerRunsPolicy());

Avoid Executors.newCachedThreadPool() in prod — unbounded thread growth.

Little's Law lens

Required concurrency ≈ throughput × latency. For IO-bound work, threads spend most time waiting, so you need more of them than cores — but always cap with a bounded queue + rejection policy and load-test the real number.

What is a daemon thread?

Easythreading▼

📌 Revision keywords

  • background
  • JVM exits

Details

  • Set via t.setDaemon(true) before start().
  • JVM exits when only daemon threads remain (e.g. GC, background schedulers).
  • Don't use daemons for work that must complete (writes may be cut off).

Note

The main thread is non-daemon; the JVM stays alive while any non-daemon thread runs. Set daemon status before start() — afterwards it throws.

What are virtual threads (Project Loom)?

Hard⭐ VIthreading▼

📌 Revision keywords

  • Java 21
  • lightweight
  • carrier thread
  • blocking is cheap

Key ideas

  • Managed by the JVM, mounted onto a few OS "carrier" threads only while running.
  • Blocking IO unmounts the virtual thread instead of pinning an OS thread — great for high-concurrency IO-bound services.
  • Write simple blocking code; get async-like scalability.
try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
  exec.submit(() -> callService());   // one virtual thread per task
}

Watch out: synchronized can "pin" a carrier thread; prefer ReentrantLock in hot paths.

Best practices

  • Don't pool virtual threads — create one per task (they're cheap).
  • Avoid synchronized around blocking calls (pins the carrier); use ReentrantLock.
  • Pairs with structured concurrency (StructuredTaskScope) for clean fan-out/fan-in.

How does garbage collection work?

Medium⭐ VIjvm▼

📌 Revision keywords

  • GC
  • HashMap
  • Objects unreachable from GC roots are collected.
  • Young gen: Eden + Survivor (Minor GC).
  • Old gen: Major/Full GC — longer pauses.

Leak

Static Map holding references forever — never collected.

Example

// leak pattern
static Map CACHE = new HashMap<>();
// fix: bounded cache, Caffeine with TTL

Foundations

  • Generational hypothesis: most objects die young → cheap Minor GCs in Eden.
  • GC roots: stack locals, static fields, JNI refs — anything reachable from these survives.
  • You can't force GC; System.gc() is only a hint.

Most "leaks" in Java are unintentional retention (static caches, listeners not removed, ThreadLocals).

Class loaders hierarchy?

  • Bootstrap → Platform → Application.

A loader asks its parent first, so core JDK classes (e.g. java.lang.String) can't be spoofed by app code — a security guarantee. Know the difference: ClassNotFoundException (not found at load time) vs NoClassDefFoundError (was there at compile, missing/failed at runtime).

  • trade-offs
  • Objects on heap; method locals and references on stack.
