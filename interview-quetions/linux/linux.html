Filesystem hierarchy, "everything is a file", shell/PATH, paths, pipes & redirection, getting help.

Explain the Linux filesystem hierarchy (key directories)

Easy⭐ VIfundamentals▼

📌 Revision keywords

  • /etc /var /home
  • /proc /tmp
  • single tree from /

Everything hangs off a single root / (no drive letters).

Key directories

  • /etc — config files
  • /var — variable data; /var/log for logs
  • /home — user home dirs; /root for root
  • /tmp — temp files (cleared)
  • /usr/bin, /bin — executables
  • /proc, /sys — virtual FS exposing kernel/process info
  • /dev — device files

On-call tip: app logs in /var/log (or journald), config in /etc, and a full /var or /tmp is a classic cause of outages.

What does "everything is a file" mean in Linux?

Mediumfundamentals▼

📌 Revision keywords

  • devices as files
  • /proc, /dev
  • uniform interface

Linux exposes most resources through the file interface, so the same open/read/write calls work for many things:

  • Regular files & directories.
  • Devices — /dev/null (discard), /dev/zero, disks /dev/sda.
  • Process info — /proc/<pid>/ (status, fd, limits).
  • Sockets and pipes (file descriptors).

This uniformity is why you can cat /proc/cpuinfo or redirect output to /dev/null — powerful and composable.

What is the shell, PATH, and environment variables?

Easyfundamentals▼

📌 Revision keywords

  • bash
  • $PATH
  • export VAR

The shell (usually bash) is the command interpreter. When you type a command, it searches the directories in $PATH to find the executable.

echo $PATH        # where commands are looked up
which java        # full path of the resolved binary
export APP_ENV=prod   # set an env var for this shell + children

Environment variables configure programs (e.g. JAVA_HOME, SPRING_PROFILES_ACTIVE). Set persistently in ~/.bashrc / /etc/environment; per-process is the 12-factor way to pass config.

Absolute vs relative paths (. .. ~ /)?

Easyfundamentals▼

📌 Revision keywords

  • / = root
  • . = here, .. = up
  • ~ = home
  • Absolute starts at root: /var/log/app.log.
  • Relative is from the current dir: logs/app.log.
  • . = current dir, .. = parent, ~ = your home, - = previous dir (cd -).

Use pwd to see where you are. In scripts/cron, prefer absolute paths — the working directory may not be what you expect.

Pipes and redirection (| > >> 2>&1)?

Medium⭐ VIfundamentals▼

📌 Revision keywords

  • | pipe
  • > / >>
  • stdout=1, stderr=2

Every process has 3 streams: stdin (0), stdout (1), stderr (2).

  • | — pipe one command's stdout into the next's stdin.
  • > overwrite a file, >> append.
  • 2>&1 — redirect stderr to wherever stdout goes.
  • > /dev/null 2>&1 — discard all output.
grep ERROR app.log | awk '{print $1}' | sort | uniq -c | sort -rn
java -jar app.jar > app.log 2>&1 &

Pipelines are the heart of Linux power — small tools composed to analyze logs in seconds.

How do you get help on a command?

Easyfundamentals▼

📌 Revision keywords

  • man
  • --help
  • which/type
  • man ls — full manual; cmd --help — quick usage.
  • which java / type cd — where a command resolves (and whether it's a builtin/alias).
  • apropos <keyword> — search man pages.

Knowing how to self-serve docs on an unfamiliar box matters more than memorizing every flag.

Navigating and listing files (ls, cd, pwd)?

Easyfiles▼

📌 Revision keywords

  • ls -la
  • ls -lh
  • ls -lt
ls -la    # long listing incl hidden (perms, owner, size, date)
ls -lh    # human-readable sizes
ls -lt    # sort by modified time (newest first) — find recent changes
ls -ltr   # oldest→newest (handy to spot the latest file at the bottom)

ls -lt is great on-call to spot what changed recently (e.g. a freshly written log or a new deploy artifact).

Viewing files — cat, less, head, tail -f?

Easy⭐ VIfiles▼

📌 Revision keywords

  • tail -f
  • less
  • head/tail -n
  • cat — dump a whole (small) file.
  • less — page through a big file (search with /, quit with q) without loading it all.
  • head -n 50 / tail -n 50 — first/last N lines.
  • tail -f app.log — follow a live log; tail -F survives log rotation.

tail -f | grep ERROR while reproducing an issue is a daily on-call move. Don't cat a multi-GB log — use less/tail.

grep — searching files/logs effectively

Medium⭐ VIfiles▼

📌 Revision keywords

  • -i -r -n -v
  • -A/-B/-C context
  • -E regex
grep -i "error" app.log         # case-insensitive
grep -rn "NullPointer" src/      # recursive + line numbers
grep -v "DEBUG" app.log          # invert: exclude
grep -C 3 "Exception" app.log    # 3 lines of context around match
grep -E "WARN|ERROR" app.log     # extended regex (OR)
grep "OrderService" app.log | grep "corr-123"  # narrow by correlation id

Combine with a correlation ID to trace one request through a noisy log. grep -c counts matches (e.g. how many errors).

find — locating files by name, size, or age

Medium⭐ VIfiles▼

📌 Revision keywords

  • -name
  • -size +100M
  • -mtime
  • -exec
find /var/log -name "*.log"             # by name
find / -size +500M 2>/dev/null          # big files (disk-full triage)
find /tmp -mtime +7 -delete             # files older than 7 days
find . -name "*.tmp" -exec rm {} \;     # run a command per match

Finding large/old files is the go-to when a disk fills up. Redirect 2>/dev/null to hide permission-denied noise.

sed and awk — when do you use them?

Hardfiles▼

📌 Revision keywords

  • sed = substitute
  • awk = columns/fields

sed — stream editor for find/replace and line edits. awk — column/field processing and quick aggregations.

sed 's/foo/bar/g' file.txt        # replace all foo with bar
sed -n '10,20p' file.txt          # print lines 10-20
awk '{print $1, $4}' access.log   # print columns 1 and 4
awk '{sum+=$5} END {print sum}'   # sum a column
awk -F',' '{print $2}' data.csv   # CSV: 2nd field

For log/CSV crunching these beat writing a script. Example: top client IPs = awk '{print $1}' access.log | sort | uniq -c | sort -rn | head.

File operations (cp, mv, rm, mkdir) and the rm -rf danger

Easyfiles▼

📌 Revision keywords

  • cp -r
  • mv
  • rm -rf (careful!)
cp -r src/ dst/      # copy recursively
mv old.txt new.txt   # move/rename
mkdir -p a/b/c       # create nested dirs
rm -rf dir/          # recursive force delete — NO undo

Safety

There is no recycle bin — rm -rf is permanent. Never run it with a variable that could be empty (rm -rf "$DIR"/ with unset $DIR = disaster). Double-check the path; consider ls first.

Archiving and compression (tar, gzip, zip)?

Easyfiles▼

📌 Revision keywords

  • tar -czf / -xzf
  • gzip
tar -czf logs.tar.gz /var/log/app/   # create gzip archive
tar -xzf logs.tar.gz                 # extract
tar -tzf logs.tar.gz                 # list contents
zcat app.log.gz | grep ERROR         # search a gzipped log without extracting

Mnemonic: create, extract, tlist; z = gzip, f = file. zcat/zgrep read rotated .gz logs directly.

Log analysis with sort, uniq, wc, cut?

Mediumfiles▼

📌 Revision keywords

  • sort | uniq -c
  • wc -l
  • cut -d
wc -l app.log                         # count lines (e.g. # of requests)
grep ERROR app.log | wc -l            # count errors
sort | uniq -c | sort -rn             # frequency count (top offenders)
cut -d',' -f2 data.csv                # extract 2nd CSV field

The classic "top errors" one-liner:

grep ERROR app.log | cut -d' ' -f5- | sort | uniq -c | sort -rn | head

uniq only collapses adjacent duplicates — always sort first.

Explain Linux file permissions and chmod

Medium⭐ VIpermissions▼

📌 Revision keywords

  • rwx
  • user/group/other
  • chmod 755 / 644

Each file has permissions for user (owner), group, others — each with r(4) w(2) x(1).

-rwxr-xr--  → owner rwx(7), group r-x(5), other r--(4) = 754
chmod 755 script.sh   # rwxr-xr-x (typical executable)
chmod 644 file.txt    # rw-r--r-- (typical data file)
chmod +x deploy.sh    # add execute (symbolic)

On a directory, x means "can enter/traverse it". A common bug: a script that won't run = missing +x; a config that won't load = wrong owner/permissions.

Changing ownership (chown, chgrp)?

Easypermissions▼

📌 Revision keywords

  • chown user:group
  • -R recursive
chown appuser:appgroup app.jar    # set owner and group
chown -R appuser /opt/app/        # recursive
chgrp devs file.txt               # just the group

Services should run as a dedicated non-root user that owns its files — so a compromised app can't touch the whole system. A common deploy issue: files owned by root that the service user can't read/write.

sudo, root, and least privilege?

Easypermissions▼

📌 Revision keywords

  • root = uid 0
  • sudo elevates
  • least privilege

root (uid 0) can do anything. sudo runs a single command with elevated rights and logs who did what (/var/log/auth.log).

Best practice: log in as a normal user, sudo only when needed, and run services as non-root. Avoid sudo su - for routine work — least privilege limits blast radius and gives an audit trail (important for a regulated platform like ICE).

Users and groups (/etc/passwd, id, groups)?

Mediumpermissions▼

📌 Revision keywords

  • /etc/passwd
  • id / whoami
  • groups
whoami            # current user
id                # uid, gid, group memberships
groups appuser    # which groups a user is in
cat /etc/passwd   # user accounts (not passwords — those are in /etc/shadow)

Groups grant shared access (e.g. add a user to a docker or log-readers group). Permissions on files are evaluated against your uid/gid, which is why id is the first thing to check on a "permission denied".

SSH and key-based login (ssh, scp)?

Mediumpermissions▼

📌 Revision keywords

  • public/private key
  • authorized_keys
  • scp
ssh user@host                 # remote shell
ssh -i key.pem user@host      # with a specific key
scp file.txt user@host:/tmp/  # copy a file over SSH

Key auth: your public key goes in the server's ~/.ssh/authorized_keys; your private key stays local (never share it). It's more secure than passwords and enables automation. A frequent gotcha: SSH refuses keys if ~/.ssh/key permissions are too open (must be 600).

Processes & Services

7 questions in this section

Inspecting processes (ps, pgrep, PID)?

Medium⭐ VIprocesses▼

📌 Revision keywords

  • ps aux
  • pgrep/pidof
  • PID / PPID
ps aux | grep java        # find the Java process + its PID, CPU, MEM
pgrep -f app.jar          # PID(s) matching a pattern
ps -ef --forest           # process tree (parent/child)
ps -o pid,%cpu,%mem,rss,cmd -p <PID>   # focused view

Every process has a PID and a parent (PPID). You'll grab the PID first, then use it with top, jstack, kill, or lsof for deeper inspection.

top/htop — and what is load average?

Medium⭐ VIprocesses▼

📌 Revision keywords

  • top / htop
  • load avg 1/5/15 min
  • vs #cores

top (or nicer htop) shows live CPU/mem per process. Press P to sort by CPU, M by memory.

Load average

The three numbers (1, 5, 15-min) are the average number of processes wanting the CPU. Compare to core count: load 8 on an 8-core box ≈ fully busy; load 16 on 8 cores = overloaded (things are queuing). A rising trend (1m > 15m) means it's getting worse.

kill and signals — SIGTERM vs SIGKILL?

Medium⭐ VIprocesses▼

📌 Revision keywords

  • SIGTERM(15) graceful
  • SIGKILL(9) forceful
  • SIGHUP reload
  • SIGTERM (15) — polite "please shut down"; the app can clean up (close connections, finish in-flight work). kill <PID> sends this by default.
  • SIGKILL (9) — kill -9 can't be caught; the OS force-kills immediately (no cleanup → possible data loss). Last resort.
  • SIGHUP (1) — often "reload config".

Graceful shutdown matters: Spring Boot + Kubernetes send SIGTERM first (drain requests), then SIGKILL after a grace period. Reflexively reaching for -9 can corrupt state.

Background jobs (&, nohup, jobs, fg/bg)?

Mediumprocesses▼

📌 Revision keywords

  • cmd &
  • nohup
  • jobs/fg/bg
long-task &            # run in background, returns the shell
jobs                   # list background jobs
fg %1                  # bring job 1 to foreground
nohup java -jar app.jar > app.log 2>&1 &   # survive logout

& backgrounds within the session; nohup (or disown) detaches it so it keeps running after you log off. For real services, prefer a proper supervisor (systemd) over nohup.

Managing services with systemd (systemctl, journalctl)?

Mediumprocesses▼

📌 Revision keywords

  • systemctl start/status
  • enable = on boot
  • journalctl -u
systemctl status myapp     # is it running? recent logs
systemctl start/stop/restart myapp
systemctl enable myapp     # auto-start on boot
journalctl -u myapp -f     # follow this service's logs
journalctl -u myapp --since "10 min ago"

systemd supervises services — auto-restart on crash, dependency ordering, and centralized logging via journald. A unit file in /etc/systemd/system/ defines how your jar starts, its user, env, and restart policy.

Scheduling with cron (crontab format)?

Medium⭐ VIprocesses▼

📌 Revision keywords

  • crontab -e/-l
  • min hr dom mon dow
crontab -e        # edit; crontab -l = list
# ┌min ┌hr ┌day ┌month ┌weekday   command
  0    2   *    *      *      /opt/app/backup.sh   # daily 02:00
  */15 *   *    *      *      /opt/app/healthcheck.sh  # every 15 min
  0    0   1    *      *      /opt/app/monthly.sh  # 1st of month

Gotchas

Cron runs with a minimal environment (limited PATH, no profile) — use absolute paths and redirect output (>> log 2>&1) or you won't see failures. For distributed apps, a scheduler/quartz with leader election avoids duplicate runs across nodes.

Process priority (nice/renice)?

Hardprocesses▼

📌 Revision keywords

  • niceness -20..19
  • lower = higher priority

Niceness hints the scheduler: range -20 (highest priority) to 19 (lowest). Default 0.

nice -n 10 ./batch.sh     # start a low-priority batch job
renice -n 5 -p <PID>       # change a running process's niceness

Use it to keep a heavy batch/report job from starving latency-sensitive services on the same box. Related: ionice for disk I/O priority.

Performance & Troubleshooting

Disk, memory, CPU, OOM killer, I/O, network, and logs — the on-call toolkit.

7 questions in this section

Disk is full — how do you find what's using it?

Medium⭐ VIperf▼

📌 Revision keywords

  • df -h
  • du -sh *
  • deleted-but-open files
df -h                      # which mount is full (Use%)
du -sh /var/* | sort -rh   # biggest dirs under /var
du -ah /var/log | sort -rh | head   # biggest files
find / -size +1G 2>/dev/null        # huge files

Classic gotcha

If df says full but du doesn't add up, a process is holding a deleted but still-open file (often a log) — space frees only when the process restarts. Find it with lsof | grep deleted. Also watch inode exhaustion (df -i) from millions of tiny files.

Checking memory (free) — used vs cached vs available?

Medium⭐ VIperf▼

📌 Revision keywords

  • free -h
  • available != free
  • swap
free -h            # total / used / free / buff/cache / available
cat /proc/meminfo  # detailed

Key insight: Linux uses spare RAM for the page cache, so low "free" is normal and healthy. Look at available (memory apps can still get) — not "free". Heavy swap usage (si/so in vmstat) means real memory pressure and will tank performance.

For a JVM, also remember the heap is bounded by -Xmx/MaxRAMPercentage — a container can OOM-kill it even when host "free" looks fine.

High CPU / high load — how do you investigate?

Hard⭐ VIperf▼

📌 Revision keywords

  • top → PID
  • vmstat/mpstat
  • us/sy/wa/id
  1. top → which process? (sort by CPU)
  2. vmstat 1 / mpstat -P ALL 1 → is it user (us), system (sy), or I/O wait (wa)?
  3. High wa = disk/network bottleneck, not CPU. High us = app compute.
  4. For a Java process, find the hot thread: top -H -p <PID> → convert thread id to hex → match it in a jstack thread dump.

That top -H + jstack trick pinpoints the exact Java method burning CPU — a strong senior-level answer.

My process was killed — what is the OOM killer?

Hardperf▼

📌 Revision keywords

  • OOM killer
  • dmesg
  • cgroup limit

When the system runs out of memory, the kernel's OOM killer kills a process (highest "oom_score", often the biggest = your JVM) to save the box.

dmesg | grep -i "killed process"   # confirm OOM kill
grep -i oom /var/log/syslog

In containers, exceeding the cgroup memory limit triggers it too (exit code 137 = 128+9/SIGKILL). Fix: right-size -Xmx vs the container limit, find the leak (heap dump), or add memory. This is distinct from a JVM OutOfMemoryError (heap exhausted inside the JVM).

Diagnosing disk I/O bottlenecks (iostat, iotop)?

Hardperf▼

📌 Revision keywords

  • iostat %util
  • iotop
  • await
iostat -x 1        # %util near 100 = disk saturated; await = latency
iotop              # which process is doing the I/O

High I/O wait (wa in top) + high %util means the disk is the bottleneck — common causes are excessive logging, a chatty DB, or swapping. Match it to a process with iotop, then reduce I/O (batch writes, async logging, faster storage).

Network checks on a box (ss, lsof, curl)?

Medium⭐ VIperf▼

📌 Revision keywords

  • ss -tlnp
  • lsof -i
  • curl -v
ss -tlnp              # listening TCP ports + owning process
ss -s                 # socket summary (incl TIME_WAIT counts)
lsof -i :8080         # who's using port 8080
curl -v http://localhost:8080/actuator/health   # test locally
nc -zv host 5432      # is the DB port reachable?

"Is my service even listening?" → ss -tlnp. "Can this box reach the DB?" → nc/curl. Lots of CLOSE_WAIT in ss = the app is leaking connections.

Where are logs and how do you search them?

Medium⭐ VIperf▼

📌 Revision keywords

  • /var/log
  • journalctl
  • tail -f | grep

System/app logs live in /var/log (e.g. syslog, auth.log, app dirs); systemd services log to journald.

tail -f /var/log/app/app.log | grep -i error
journalctl -u myapp --since "1 hour ago" | grep corr-123
zgrep "Exception" /var/log/app/app.log.*.gz   # rotated logs

Filter by correlation ID to follow one request. Note: production logs should be shipped to a central aggregator (ELK/Loki) — grepping a single box is for quick triage.

Running Java Apps on Linux

Launching the JVM, file descriptors/ulimit, env config, log pipelines, on-call debugging.

5 questions in this section

How do you run and manage a Java app on a Linux server?

Mediumjava▼

📌 Revision keywords

  • java -jar
  • -Xmx flags
  • systemd service
java -XX:MaxRAMPercentage=75 -jar app.jar --spring.profiles.active=prod
# inspect a running JVM:
jps -l            # list JVMs + main class
jstack <PID>       # thread dump
jmap -histo <PID>  # heap histogram

For real services, run under systemd (auto-restart, logging) or in a container, as a non-root user. Pass config via env/args (12-factor), and use container-aware JVM flags (MaxRAMPercentage) instead of a hard-coded -Xmx.

"Too many open files" — what's happening and how to fix it?

Hard⭐ VIjava▼

📌 Revision keywords

  • ulimit -n
  • fd = files + sockets
  • leak vs limit

Every open file and socket is a file descriptor. Hitting the per-process limit throws Too many open files.

ulimit -n                 # current fd limit (often 1024 default — too low)
ls /proc/<PID>/fd | wc -l  # how many the process holds now
lsof -p <PID> | wc -l      # detailed

Two causes: the limit is too low (raise it via limits.conf / systemd LimitNOFILE), or the app is leaking connections/streams (not closing HTTP/DB clients, sockets stuck in CLOSE_WAIT). Fix the leak (try-with-resources, connection pooling) rather than only bumping the limit.

Passing configuration via environment variables?

Easyjava▼

📌 Revision keywords

  • export
  • SPRING_*
  • 12-factor config
export SPRING_PROFILES_ACTIVE=prod
export SPRING_DATASOURCE_URL=jdbc:postgresql://db:5432/app
java -jar app.jar
printenv | grep SPRING     # verify what the process will see

Spring Boot maps env vars to properties (SPRING_DATASOURCE_URL → spring.datasource.url), so the same image runs in every environment — the 12-factor way. Keep secrets in a vault/secret manager, not in plain env files or shell history.

Quickly analyzing app logs with a pipeline?

Medium⭐ VIjava▼

📌 Revision keywords

  • grep | awk | sort | uniq -c
  • tail -f
# count errors per hour
grep ERROR app.log | awk '{print $1, $2}' | cut -c1-13 | sort | uniq -c

# most frequent exception types
grep -oE "[A-Za-z.]+Exception" app.log | sort | uniq -c | sort -rn | head

# follow live errors for one request
tail -f app.log | grep --line-buffered corr-abc123

These one-liners answer "is it spiking?", "what's the top error?", and "what happened to this request?" in seconds — exactly what you do before pulling up a dashboard.

Walk through debugging a slow/down Java service on a Linux box

Hard⭐ VIjava▼

📌 Revision keywords

  • is it up? logs? resources?
  • thread/heap dump
  • mitigate then root-cause

A systematic pass

  1. Is it running & listening? systemctl status / ps / ss -tlnp.
  2. Logs: journalctl -u app -f / tail -f | grep ERROR + correlation ID.
  3. Resources: top (CPU/mem), free -h, df -h (full disk?), I/O wait.
  4. If hung/CPU-spinning: jstack thread dump (+ top -H); if OOM: heap dump / check dmesg for the OOM killer.
  5. Recent change? Last deploy / config diff — usually the culprit.

Mindset: mitigate first (restart/rollback/scale to restore service), then root-cause with the dumps + logs and add a guardrail so it can't recur.
