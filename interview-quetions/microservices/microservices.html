Microservices Fundamentals

When to split, bounded contexts, migration — architecture basics.

Microservices vs monolith — trade-offs?

Easy⭐ VIfundamentals▼

📌 Revision keywords

  • Monolith:
  • Microservices:
  • monolith
  • ACID
  • CI
  • CD
  • API
  • Telco

Monolith: single deployable, simple debugging, ACID transactions in one DB. Microservices: independent deploy/scale per service, team ownership per bounded context.

Costs of microservices

  • Distributed failures, networking latency
  • Data consistency across services harder
  • Need observability, CI/CD maturity, API contracts

When to split

When scaling, release cadence, or team boundaries are blocked by monolith — not because it is fashionable.

Your angle

Telco BSS is already distributed; you worked integration microservices (Camel) around legacy cores, not a greenfield Netflix stack.

The middle ground

Don't forget the modular monolith — clean module boundaries in one deployable. Many teams should start there and extract services only when scaling/team pain is real (Martin Fowler's "MonolithFirst"). Remember Conway's Law: your architecture mirrors your org structure.

What is a bounded context (DDD)?

Medium⭐ VIfundamentals▼

📌 Revision keywords

  • Order
  • microservice

Each microservice owns one business capability with its own ubiquitous language and data model. Order in billing ≠ Order in provisioning — don't share one giant entity table across teams.

APIs translate between contexts; anti-pattern is shared database with tight coupling.

Context mapping

Between contexts, use an Anti-Corruption Layer (a translation layer) so a legacy/partner model doesn't leak into your clean domain — exactly the role your Camel integration routes play around legacy BSS cores.

When should you split into a new microservice?

Mediumfundamentals▼

📌 Revision keywords

  • Don't split
  • microservice
  • API
  • Clear bounded context and independent scaling need
  • Different release cadence or team ownership
  • Technology fit (e.g. integration engine vs CRUD API)

Don't split for tiny features — operational tax (deploy, monitor, on-call) per service is real.

Interview line

"Extract a service to solve a specific problem (independent scaling, release cadence, team ownership, or a tech mismatch) — not speculatively." Every new service adds deploy, monitoring, and on-call cost.

Strangler fig pattern for legacy migration?

Mediumfundamentals▼

📌 Revision keywords

  • BSS
  • Put facade/gateway in front of legacy; route incrementally to new services.
  • Old system shrinks over time.
  • Common in telecom when replacing BSS modules without big-bang cutover.

How to execute safely

  1. Put a facade/gateway in front of the legacy system.
  2. Route one capability at a time to the new service.
  3. Parallel-run and compare outputs before cutting over.
  4. Decommission the old path once verified.

Lets you migrate with no big-bang risk and an easy rollback (flip the route back).

Loose coupling vs high cohesion?

Easyfundamentals▼

📌 Revision keywords

  • Cohesion:
  • Coupling:

Cohesion: everything inside one service relates to one job. Coupling: minimize knowledge of other services' internals — interact via stable APIs/events only.

Kinds of coupling to avoid

Beyond code coupling, watch temporal coupling (service A is down → B fails) and data coupling (shared tables). Asynchronous events reduce temporal coupling; database-per-service removes data coupling.

Why is a shared database an anti-pattern?

Medium⭐ VIfundamentals▼

📌 Revision keywords

  • In simple terms:
  • why
  • Services can't evolve schema independently; one team's migration breaks another.
  • Hidden coupling via joins across domains.
  • Prefer database-per-service + APIs/events for cross-domain reads.

Migration path

Break a shared DB gradually: expose data via an API, build a per-service read model, and use CDC (Debezium) or events to keep copies in sync. Don't try to split the schema in one big move.

What does independent deployability mean?

Easyfundamentals▼

📌 Revision keywords

  • Jenkins
  • Deploy service A without redeploying B.
  • Requires backward-compatible APIs, feature flags, contract tests.
  • Jenkins pipelines per repo at Optima/Vodafone style orgs.

What makes it possible

Backward/forward-compatible contracts + expand-contract (parallel-change) DB migrations: add the new column/endpoint, deploy, migrate readers, then remove the old — so producer and consumer can deploy on different days.

Sync REST vs async messaging between services?

Medium⭐ VIcommunication▼

📌 Revision keywords

  • REST
  • Telco
  • JMS
  • Kafka

Sync REST

Simple request-response, easy to debug. Downside: cascading latency, tight runtime coupling, both must be up.

Async messaging

Decouples peak load, buffers with queue, multiple subscribers. Harder tracing; need idempotency.

Telco pattern

Sync for real-time eligibility; async JMS/Kafka for provisioning steps taking minutes.

How to choose

Use sync (REST/gRPC) when the caller needs an immediate answer; use async (events/queues) to decouple, absorb spikes, and survive downstream outages. Orchestration (a coordinator calls steps) vs choreography (services react to events) is the related design choice.

API gateway role in microservices?

Easycommunication▼

📌 Revision keywords

  • API
  • REST
  • JWT
  • Single north-south entry: TLS, auth, rate limit, routing to internal services.
  • No business logic.
  • Vodafone REST likely behind corporate gateway + LDAP/JWT.

Responsibilities & caution

Cross-cutting concerns live here: routing, authn/z, rate limiting, TLS termination, request aggregation. Keep business logic out of the gateway, and run it HA — it's a single point of failure if you don't.

When gRPC instead of REST?

Mediumcommunication▼

📌 Revision keywords

  • REST
  • HTTP
  • Telco
  • XML
  • Binary, HTTP/2, strong contracts (protobuf), lower latency — great service-to-service.
  • REST better for browser/public partners.
  • Telco partners often still XML/REST/SOAP.

When gRPC wins

Internal east-west calls needing low latency, strong typing (Protobuf contracts), and streaming over HTTP/2. Downsides: not browser-native (needs grpc-web), binary payloads are harder to debug. Use REST/JSON at the public edge, gRPC between services.

Event-driven architecture basics?

Medium⭐ VIcommunication▼

📌 Revision keywords

  • OrderCreated

Service A publishes OrderCreated; B and C subscribe without A knowing them. Loose coupling; eventual consistency. Need schema registry/versioning for events.

Pick the event style

  • Event notification — "something happened", consumer calls back for details.
  • Event-carried state transfer — event includes the data (no callback).
  • Event sourcing — the event log is the source of truth.

Use a schema registry + versioned events so producers and consumers evolve safely.

API versioning and backward compatibility?

Mediumcommunication▼

📌 Revision keywords

  • API
  • Prefer additive changes.
  • Breaking changes → new version or parallel endpoint.
  • Deprecation timeline + consumer contract tests.
  • Partner integrations (XL Axiata) need certification windows.

Golden rule

Never break existing consumers — use the expand-contract approach: add new fields as optional, support N-1, and announce removal. Consumer-driven contracts tell you who still depends on the old shape.

What is consumer-driven contract testing?

Mediumcommunication▼

📌 Revision keywords

  • API
  • CI
  • Consumer defines expected API shape; provider verifies in CI (Pact).
  • Catches breaking changes before deploy — critical when 10+ teams consume your integration API.

How it works

Tools like Pact let the consumer publish expectations; the provider verifies them in CI. This catches breaking changes before deploy without spinning up the whole system — much faster and more reliable than end-to-end tests.

Service discovery and load balancing?

Mediumcommunication▼

📌 Revision keywords

  • telco
  • Dynamic: Eureka, Consul, K8s DNS — client asks registry for healthy instances.
  • Static: hardware LB + config — common on-prem telco.
  • Health checks remove bad pods/nodes.

Two models

Client-side (Eureka/Consul + client load balancing) vs server-side (a load balancer / Kubernetes Service + DNS). On K8s you usually get discovery for free via Service DNS, so you rarely need Eureka.

Backend for Frontend (BFF) pattern?

Mediumcommunication▼

📌 Revision keywords

  • API
  • Separate API tailored per client (mobile vs web) aggregating multiple microservices — avoids fat generic API and over-fetching.
  • One BFF per client type, not per developer.

Why BFF

A Backend-for-Frontend tailors aggregation/shaping per client (web vs mobile) so each UI isn't bloated by the others' needs. It avoids one giant general-purpose gateway becoming a bottleneck and a shared chokepoint.

What is a service mesh (Istio/Linkerd)?

Hardcommunication▼

📌 Revision keywords

  • telco
  • Sidecar proxy handles mTLS, retries, telemetry uniformly — policy without changing app code.
  • Trade-off: operational complexity.
  • Many telco on-prem stacks use LB + libraries (Resilience4j) instead.

What it gives you

A mesh (Istio/Linkerd) runs a sidecar proxy next to each service to provide mTLS, retries, timeouts, traffic shifting, and telemetry — without changing app code. Trade-off: extra operational complexity and per-hop latency; adopt when you have many services.

Resilience & Scale

Timeouts, retries, idempotency, 1M+ txn/day operations.

8 questions in this section

Circuit breaker, bulkhead, timeout — resilience triad?

Medium⭐ VIresilience▼

📌 Revision keywords

  • circuitBreaker
  • Timeout
  • Circuit breaker
  • Bulkhead
  • cap
  • API
  • Camel
  • SLA
  • Timeout — cap wait, fail fast
  • Circuit breaker — stop calling failing dependency (closed → open → half-open probe)
  • Bulkhead — limit concurrent calls per partner so one slow API doesn't exhaust thread pool

Resilience4j or Camel circuitBreaker policy — align timeouts with partner SLA.

States & config

Three states: closed (normal) → open (fail fast after error threshold) → half-open (trial requests to test recovery). With Resilience4j: failureRateThreshold, waitDurationInOpenState, sliding window. Pair with a timeout and a fallback.

Retry with exponential backoff?

Medium⭐ VIresilience▼

📌 Revision keywords

  • cap
  • idempotent
  • Retry transient failures (network blip) with increasing delay + jitter.
  • Max attempts cap.
  • Never retry non-idempotent POST without idempotency key.
  • Pair with circuit breaker when partner is down.

Do it safely

  • Only retry idempotent operations and transient errors (timeouts, 503) — never a 400.
  • Use exponential backoff + jitter to avoid retry storms/thundering herd.
  • Cap with a retry budget; combine with a circuit breaker.

Idempotency in distributed integrations?

Medium⭐ VIresilience▼

📌 Revision keywords

  • idempotentConsumer
  • Camel

Same message twice → same outcome. Store idempotency key (messageId, orderId) in DB/Redis with TTL. Camel: idempotentConsumer. Critical for billing/charge routes.

Implementation

Client sends an Idempotency-Key; server stores key→result with a unique constraint and returns the saved result on replay. Essential because queues/Kafka deliver at-least-once (duplicates are normal).

Dead letter queue and poison messages?

Medium⭐ VIresilience▼

📌 Revision keywords

  • DLQ
  • After max redeliveries, move message to DLQ for manual inspection/replay.
  • Poison message = always fails validation — fix data or skip with audit.
  • Don't infinite redelivery loop.

Lifecycle

After N failed retries, route the message to a dead-letter queue, alert, and provide a replay path once the bug is fixed. A "poison" message (always fails) must be quarantined so it doesn't block the partition/queue.

Backpressure when consumer is slow?

Mediumresilience▼

📌 Revision keywords

  • SLO
  • Queue depth grows; apply consumer scaling, throttle producers, or temporary shed load.
  • Monitor queue age — oldest message age is key SLO.

Techniques

Bounded queues (block/reject when full), reactive streams (Flux request-n), and load shedding (return 429/503 early) protect a service from being overwhelmed. The producer must slow down or be rejected — never buffer unboundedly (OOM).

Graceful degradation vs fail fast?

Mediumresilience▼

📌 Revision keywords

  • In simple terms:
  • trade-offs
  • Degrade: return cached/stale data when non-critical dependency down.
  • Fail fast: return 503 when cannot fulfill safely (payments).
  • Document which paths allow degraded mode.

Graceful degradation

When a dependency is down, return a cached/last-known value, a sane default, or a partial response instead of failing the whole request. Feature flags let you turn off non-critical features under load to protect the core path.

Chaos engineering in microservices?

Hardresilience▼

📌 Revision keywords

  • In simple terms:
  • Chaos engineering in microservices
  • Inject failures (kill pod, latency) in controlled env to verify resilience.
  • Start with game days; don't chaos prod without maturity.
  • Validates timeouts and fallbacks actually work.

Do it scientifically

Form a hypothesis ("if the payment DB is slow, checkout still degrades gracefully"), limit the blast radius, inject the failure (latency, pod kill) during a planned game day, and verify alerts + recovery. Tools: Chaos Monkey / Litmus.

Data & Consistency

Saga, outbox, eventual consistency, CAP in distributed systems.

8 questions in this section

Distributed transactions: 2PC vs Saga?

Hard⭐ VIconsistency▼

📌 Revision keywords

  • 2PC:
  • Saga:
  • Saga

2PC: blocking, fragile across heterogeneous systems — rare in microservices. Saga: sequence of local transactions; on failure run compensating steps (cancel reservation, reverse charge).

Styles

Choreography (events) vs orchestration (Camunda). XL Axiata: BPMN for long order flows.

vs distributed transactions

You can't use 2-phase-commit across services (slow, tight coupling), so a saga is a sequence of local transactions, each with a compensating action to undo on failure (e.g. refund if shipping fails). It trades atomicity for availability + eventual consistency.

Saga pattern — choreography vs orchestration?

Hard⭐ VIconsistency▼

📌 Revision keywords

  • Saga

Choreography

Services react to events; no central brain — can become hard to trace.

Orchestration

Central coordinator (Camunda, custom) calls participants — clearer visibility, single place for timeouts/compensation.

Your pitch

Telecom order: reserve → charge → provision → notify; compensating cancel if provision fails.

Orchestration vs choreography

  • Orchestration — a central coordinator drives steps (easier to reason about/monitor; coordinator is a dependency).
  • Choreography — services react to each other's events (loose, but flow is implicit and harder to trace).

Your XL Axiata Camunda work is orchestration.

What is eventual consistency?

Mediumconsistency▼

📌 Revision keywords

  • In simple terms:
  • eventual consistency
  • Replicas/services converge over time; reads may be stale briefly.
  • Acceptable for analytics, notifications; not for account balance without careful design.
  • UI: show pending state.

Making it usable

Handle the lag explicitly: read-your-writes (read from primary right after a write), idempotent consumers, and a reconciliation/repair job for drift. Tell the user "processing" rather than pretending it's instant.

Transactional outbox pattern?

Hard⭐ VIconsistency▼

📌 Revision keywords

  • same DB transaction
  • Transactional
  • Kafka
  • JMS

Write business row + outbox event in same DB transaction. Separate publisher reads outbox and sends to Kafka/JMS — avoids dual-write (DB committed, message lost).

The problem it solves

The dual-write problem: you can't atomically write to the DB and publish to Kafka. The outbox writes the event to an outbox table in the same DB transaction; a relay (CDC/Debezium or a poller) publishes it reliably afterward.

CQRS — when separate read and write models?

Hardconsistency▼

📌 Revision keywords

  • SQL
  • Write model normalized; read model denormalized for fast queries/reports.
  • Sync via events.
  • Vodafone reporting: tuned SQL/read replicas vs OLTP write schema.

When it's worth it

Split the write model from optimized read models when read and write workloads/shapes diverge a lot (e.g. complex dashboards over transactional data). Cost: more moving parts + eventual consistency between models — don't apply it everywhere.

Database per service — practical reality?

Mediumconsistency▼

📌 Revision keywords

  • telco
  • Ideal: each service owns schema.
  • Reality in telco: legacy shared Oracle still exists — strangle and wrap with APIs.
  • New microservices get own schema/user credentials.

Cross-service queries

Since you can't JOIN across service DBs, use API composition (call each service and merge) for simple cases or a CQRS read model (materialize a view from events) for complex/high-volume reporting.

CAP theorem — what do you say in interviews?

Mediumconsistency▼

📌 Revision keywords

  • CAP
  • During partition, choose consistency (CP) or availability (AP).
  • Most microservices under partition pick availability + eventual consistency for non-critical paths; payment paths favor consistency with careful design.

Go beyond CAP

During a partition you choose Consistency or Availability; the more practical model is PACELC — Else (no partition) you still trade Latency vs Consistency. Example: a bank balance leans CP, a product catalog leans AP.

Exactly-once delivery — possible?

Hard⭐ VIconsistency▼

📌 Revision keywords

  • at-least-once
  • idempotent
  • Kafka

True end-to-end exactly-once is extremely hard. Practical: at-least-once transport + idempotent consumers + dedup store. Kafka idempotent producer helps but consumer still must dedupe.

The honest answer

True exactly-once delivery is impossible across a network; you achieve effectively-once via idempotent consumers + a dedup store. Kafka offers exactly-once processing within Kafka (transactions + idempotent producer), but external side effects still need idempotency.

What is Apache Camel? Why in telecom integrations?

Medium⭐ VIcamel▼

📌 Revision keywords

  • Route:
  • Exchange:
  • Camel
  • HTTP
  • JMS
  • Kafka
  • XML
  • OSS

Integration framework with Enterprise Integration Patterns: routes, endpoints (HTTP, JMS, FTP, Kafka), transformers, error handlers — Java DSL or XML.

Core concepts

Route: from → processors → to. Exchange: message body + headers. Reduces boilerplate for retry, multicast, wire tap.

Your experience

Optima: Camel microservices bridging OSS/BSS at 1M+ txn/day on Fuse/Karaf-style stacks.

What it is

Apache Camel is an integration framework implementing the Enterprise Integration Patterns with 300+ components (HTTP, JMS, Kafka, file, SQL...) and a routing DSL. It's the glue between systems — ideal for telco BSS where you bridge many protocols/legacy endpoints.

Structure of a Camel route?

Easycamel▼

  • routeId
  • onException
  • Camel

from('jms:queue:in') consumer → process/transform → to('http://partner/api') producer. routeId for monitoring; onException for error handling; headers carry correlation metadata.

Anatomy

from("kafka:orders")
  .routeId("order-route")
  .process(this::validate)
  .to("jms:queue:provisioning");

A route = consumer endpoint (from) → processors/EIPs → producer endpoint(s) (to), defined in a RouteBuilder.

Easykafka-ms▼

Why Kafka

It's the async backbone: decouples producers from consumers, buffers spikes, and—because it's a retained log—lets you replay history and add new consumers later without the producer knowing. Great for event-driven integration around legacy cores.

Kafka vs traditional JMS (ActiveMQ)?

Mediumkafka-ms▼

📌 Revision keywords

  • Kafka
  • JMS
  • Telco
  • Camel
  • JMS: queue/topic, broker deletes after ack — good for task queues.
  • Kafka: log retained, replay, high throughput — good for event streaming.
  • Telco often has both; Camel abstracts via same route DSL.

Log vs queue

JMS = a queue (message consumed/removed, broker tracks state). Kafka = a durable log (messages retained; consumers track their own offset, multiple consumer groups read independently, replay is possible). Kafka scales out via partitions.

Ordering guarantees across microservices?

Mediumkafka-ms▼

📌 Revision keywords

  • Kafka
  • idempotent
  • Kafka: order within partition only — use same partition key (customerId).
  • Global order is expensive; design for eventual consistency and idempotent handlers.

How ordering works

Kafka guarantees order only within a partition. Route related events to the same partition via a key (e.g. accountId) to keep per-entity order. The trade-off: one partition per key path limits parallelism, so choose the key carefully.
