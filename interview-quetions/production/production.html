  2. Check dashboard + recent deploys + partner status
  3. Mitigate first (restore service), debug second
  4. Update incident channel; escalate if needed
  5. Post-incident: timeline, root cause, action items

The flow

Acknowledge → assess impact/scope → mitigate (rollback/flag/scale) → communicate status → escalate if needed → clean handoff with notes. Your job during an incident is to restore service, not to find the perfect fix.

MTTR vs MTTD — explain and improve them?

Medium⭐ VIIncidents▼

📌 Revision keywords

  • MTTD
  • MTTR
  • SLO
  • Runbooks, one

MTTD (mean time to detect): how fast you know something broke. MTTR (mean time to recover): detect → stable again.

Improve MTTD

  • SLO-based alerts on error rate/latency, not only process down
  • Synthetic checks on critical APIs

Improve MTTR

  • Runbooks, one-click rollback, correlation IDs in logs
  • Safe defaults: circuit breakers, bulkheads

Optimize recovery

MTTD (detect) + MTTR (recover) define how bad an incident feels. You usually get more value lowering MTTR (fast rollback, runbooks, good alerts) than chasing zero failures. Track both and review them in post-mortems.

When do you take thread dump vs heap dump?

HardDebugging▼

📌 Revision keywords

  • jstack
  • /threaddump
  • Thread dump:
  • Heap dump:

Thread dump: app hung, high CPU, deadlock — see blocked threads. jstack or Actuator /threaddump.

Heap dump: OutOfMemoryError, suspected memory leak — analyze with MAT (dominator tree). Heavy — use off-peak.

Take during incident before restart destroys evidence.

Which tool when

Hung/slow + high CPU → thread dump (jstack, take 2–3) to find stuck/looping threads or a deadlock. OOM/memory growth → heap dump (jmap / -XX:+HeapDumpOnOutOfMemoryError) analyzed in MAT's dominator tree.

Liveness vs readiness probes (K8s)?

Medium⭐ VIHealth▼

📌 Revision keywords

  • Liveness:
  • Readiness:
  • Liveness: process alive? Fails → restart pod (fix deadlock)
  • Readiness: can accept traffic? Fails → remove from load balancer (DB down, warming up)

Don't put slow external partner checks on liveness — flapping restarts. Readiness can fail when dependencies unhealthy.

Key distinction

Liveness fails → orchestrator restarts the pod; readiness fails → stop routing traffic but keep it running. Don't check downstream deps in liveness or one transient blip restart-loops the whole fleet.

SLI vs SLO vs SLA — simple example?

Hard⭐ VISLO▼

📌 Revision keywords

  • SLI:
  • SLO:
  • SLA:
  • SLO
  • SLA
  • API
  • SLI: measured metric — e.g. % of provisioning API calls < 2s
  • SLO: target — 99.5% of calls < 2s over 30 days
  • SLA: contract with penalties — stricter, customer-facing

Error budget: if SLO 99.9%, you can "spend" 0.1% downtime on releases and experiments.

The vocabulary

SLI = the measured number (e.g. % of requests < 200ms); SLO = the target (99.9%); the error budget = 1 − SLO. Burning the budget fast → slow down and stabilize; budget healthy → ship features. It makes reliability vs velocity a data-driven decision.

HikariCP pool exhaustion — symptoms and fix?

Medium⭐ VIJVM▼

📌 Revision keywords

  • Symptoms:
  • Causes:
  • Fix:
  • spring

Symptoms: threads blocked waiting connection, timeouts, "Connection is not available".

Causes: pool too small, slow queries hold connections, connection leak (not closed).

Fix: right-size pool (~ cores * 2 + disk), fix long transactions, leak detection, query tuning.

spring.datasource.hikari.maximum-pool-size=20
spring.datasource.hikari.leak-detection-threshold=60000

HikariCP essentials

Pool size is usually small (often ~CPU-bound, e.g. (cores×2)+disks), not huge — too big overwhelms the DB. Watch for pool exhaustion (all connections held by slow queries/leaks) and enable leakDetectionThreshold. Always set connection/query timeouts.

JVM heap and GC issues in production?

MediumJVM▼

📌 Revision keywords

  • JVM
  • GC
  • Camel
  • Watch heap usage trend, GC pause time.
  • Frequent Full GC → memory leak or heap too small.
  • G1GC common on Java 11+.

Caching in production — risks?

MediumPerformance▼

📌 Revision keywords

  • Telco
  • Stale data, cache stampede, invalidation bugs.

Timeouts and retries in production integrations?

Medium⭐ VIReliability▼

📌 Revision keywords

  • errorHandler
  • redeliveryPolicy
  • idempotent
  • Camel
  • Always set connect + read timeouts.
  • Retries only on idempotent ops with exponential backoff and max attempts.
  • Unbounded retry amplifies outages (retry storm).

Camel: errorHandler, redeliveryPolicy with delay; dead letter after N failures.

The non-negotiables

Every remote call gets a timeout (no infinite waits). Retry only idempotent ops on transient errors, with exponential backoff + jitter and a retry budget, behind a circuit breaker. Unbounded retries cause retry storms that amplify an outage.

Dead letter queue — purpose and handling?

Medium⭐ VIDLQ▼

📌 Revision keywords

  • DLQ

Messages that failed max retries go to DLQ for manual inspection — bad payload, schema change, partner permanent 400.

Don't auto-replay all without fix; replay one message with correlation ID after root cause. Alert on DLQ depth threshold.

Operate the DLQ

Alert when messages land in the DLQ, inspect to find the root cause (bad data vs bug), fix, then replay from the DLQ. A growing DLQ is a silent data-loss risk if nobody watches it.

Why idempotency matters in async production?

Medium⭐ VIQueues▼

📌 Revision keywords

  • Camel
  • idempotent
  • At-least-once delivery → duplicate messages.
  • Store processed message ID or business key (orderId) in DB before side effect.

Why essential

Queues/Kafka deliver at-least-once, so duplicates are normal. Dedup on a business key (processed-IDs table / unique constraint) or make the write an upsert — then reprocessing is harmless and retries/replays are safe.

When is replay safe vs dangerous?

HardReplay▼

📌 Revision keywords

  • Safe:
  • Dangerous:
  • idempotent

Safe: downstream idempotent, replay from offset after fix, billing already deduped by transaction ID.

Dangerous: double charge, duplicate provisioning — need compensating transaction or strict idempotency keys.

How

Because Kafka retains the log, you can reset a consumer group's offset and reprocess from a point in time — great for recovering from a consumer bug or rebuilding a read model. Only safe if consumers are idempotent.

JMS (ActiveMQ) for classic point-to-point work queues with per-message acks and priorities; Kafka for high-throughput event streaming, multiple independent consumers, and replay. Telco integration often uses both — JMS to legacy, Kafka as the event backbone.
