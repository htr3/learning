Spring vs Spring Boot?

Easy⭐ VIcore▼

📌 Revision keywords

  • SpringBootApplication
  • application.yml
  • Spring Framework
  • Spring Boot
  • Spring
  • Boot
  • XML

Spring Framework is the core IoC/DI container plus modules (MVC, Data, Security). You wire XML/Java config, pick versions, embed Tomcat yourself.

Spring Boot is opinionated auto-configuration on top: starters bundle dependencies, @SpringBootApplication enables component scan + auto-config, embedded server, application.yml, Actuator. You focus on business code; Boot picks sensible defaults.

What problems Boot solved

  • Dependency hell — starters + a managed parent POM give compatible, tested versions, so you don't hand-pick library versions.
  • Config boilerplate — no more XML DispatcherServlet / view resolver / datasource wiring; auto-config infers it.
  • Deployment — an embedded Tomcat/Netty means one runnable fat JAR instead of deploying a WAR to an external server.

Key Boot features

  • Auto-configuration (conditional on classpath)
  • Starters (curated dependency sets)
  • Embedded server (Tomcat/Jetty/Undertow/Netty)
  • Externalized config + profiles (application.yml)
  • Actuator (health, metrics, info)

When plain Spring still applies

You still use the Spring Framework itself for everything — Boot just configures it. You might avoid Boot only for very constrained/legacy environments or when you need total control over wiring (rare).

Interview line

Boot does not replace Spring — it accelerates building production-ready Spring apps with less boilerplate. "Convention over configuration."

What does @SpringBootApplication do?

Medium⭐ VIcore▼

📌 Revision keywords

  • Configuration
  • EnableAutoConfiguration
  • ComponentScan
  • Component
  • Service
  • SpringApplication.run(Main.class, args)

It's a meta-annotation (one annotation that bundles three):

  • @Configuration — marks the class as a source of bean definitions
  • @EnableAutoConfiguration — loads auto-config classes from the classpath (conditional on jars present)
  • @ComponentScan — scans the package of the main class and sub-packages for @Component, @Service, @Repository, @Controller

Example

@SpringBootApplication
public class Application {
  public static void main(String[] args) {
    SpringApplication.run(Application.class, args);
  }
}

Entry point: SpringApplication.run(Application.class, args) bootstraps the app — creates the ApplicationContext, runs auto-configuration, starts the embedded server, and fires any CommandLineRunner/ApplicationRunner beans.

Common gotcha

Component scanning starts at the main class's package. If your beans live in a package above or outside that package, they won't be picked up — keep the main class in a root package, or add @ComponentScan(basePackages = "...").

Interview tip

If asked to customize: you can exclude specific auto-configs with @SpringBootApplication(exclude = DataSourceAutoConfiguration.class).

Constructor injection — why preferred?

Easy⭐ VIcore▼

📌 Revision keywords

  • final
  • Autowired
  • Spring
  • Dependencies explicit in constructor
  • Dependencies explicit in constructor — easy to test (pass mocks, no reflection)
  • Fields can be final — immutable, thread-safe
  • Fails fast at startup if a bean is missing (not an NPE at runtime)
  • Avoids field injection hiding large dependency lists (a long constructor is a visible code smell nudging you to split the class)
  • No need for the reflection-based @Autowired field hacks in tests

Example

@Service
public class OrderService {
  private final OrderRepository repo;
  private final PaymentClient payment;

  // single constructor → @Autowired optional (Spring 4.3+)
  public OrderService(OrderRepository repo, PaymentClient payment) {
    this.repo = repo;
    this.payment = payment;
  }
}

The three injection types

  • Constructor — preferred (immutable, testable).
  • Setter — for optional dependencies or to break a circular dependency.
  • Field (@Autowired on a field) — concise but hides dependencies and can't be final; avoid in production code.

Spring 4.3+: a single constructor needs no @Autowired. Lombok's @RequiredArgsConstructor generates the constructor for final fields.

Bean scopes in Spring?

Mediumcore▼

📌 Revision keywords

  • singleton
  • prototype
  • request / session / application
  • Spring
  • singleton (default) — one shared instance per Spring container
  • prototype — a new instance on every injection / getBean()
  • request — one per HTTP request (web)
  • session — one per HTTP session (web)
  • application — one per ServletContext (web)
  • websocket — one per WebSocket session

The classic gotcha

A prototype bean injected into a singleton is resolved once at singleton creation — so you get the same prototype instance every time, not a fresh one. Fixes: inject ObjectProvider<T> / Provider<T>, use method injection (@Lookup), or set proxyMode on the scope.

Thread-safety reminder

Because singletons are shared across all request threads, never store request/mutable state in singleton fields — keep beans stateless (this is the #1 multi-tenant/web concurrency bug).

Most services and components are singletons by design; reserve other scopes for genuinely per-request/per-session state.

How do you fix a circular dependency?

Hard⭐ VIcore▼

📌 Revision keywords

  • Lazy
  • PostConstruct
  • Spring
  • Redesign

A needs B, B needs A — with constructor-only injection Spring can't construct either one first, so on startup you get a BeanCurrentlyInCreationException. (Since Spring Boot 2.6, circular references are disallowed by default rather than silently resolved.)

Fixes (best first)

  1. Redesign — the cycle usually signals a design problem; extract the shared logic into a third bean both can depend on (best fix).
  2. @Lazy on one dependency — Spring injects a proxy and delays real initialization until first use, breaking the construction cycle.
  3. Setter/field injection on one side — the bean is created first, then the dependency is set (less ideal, loses final).
  4. @PostConstruct manual wiring — last resort.

Example fix with @Lazy

@Service
public class A {
  private final B b;
  public A(@Lazy B b) { this.b = b; }   // proxy breaks the cycle
}

Interview tip

Say the cycle is a smell first, then list the mechanical fixes — interviewers want to hear "I'd redesign," not just "@Lazy it."

What are Spring Boot starters?

Medium⭐ VIcore▼

📌 Revision keywords

  • spring-boot-starter-web
  • starter-data-jpa
  • Spring
  • Boot
  • jpa

Curated dependency sets that bundle everything you need for a capability: spring-boot-starter-web brings Spring MVC, Jackson, and embedded Tomcat; spring-boot-starter-data-jpa brings Hibernate, HikariCP, and a transaction manager.

Common starters

  • spring-boot-starter-web — REST/MVC + Tomcat
  • spring-boot-starter-data-jpa — JPA/Hibernate
  • spring-boot-starter-security — Spring Security
  • spring-boot-starter-actuator — health/metrics
  • spring-boot-starter-test — JUnit 5, Mockito, AssertJ, Spring Test
  • spring-boot-starter-validation — Bean Validation

How it ties together

Starter (jar on classpath) + auto-configuration = add the dependency → the feature appears, configured from properties. The spring-boot-starter-parent (or the dependency-management BOM) pins compatible versions so you only declare the starter, not version numbers.

Note

You can also write your own custom starter (like your MS-Builder generated services) to standardize cross-team setup.

Profiles and externalized configuration?

Easycore▼

📌 Revision keywords

  • spring.profiles.active=dev
  • application-dev.yml
  • SPRING_DATASOURCE_URL
  • spring

spring.profiles.active=dev loads application-dev.yml on top of the base application.yml. Use profiles for per-environment DB URLs, log levels, and feature flags (dev / test / staging / prod).

Property resolution order (high → low priority)

  1. Command-line args
  2. Environment variables / system properties
  3. application-{profile}.yml
  4. application.yml (defaults)

So in prod, an env var like SPRING_DATASOURCE_URL overrides whatever is in YAML — that's the 12-factor approach.

Profile-specific beans

@Bean
@Profile("prod")
public DataSource prodDataSource() { ... }

Secrets

Never commit secrets to YAML/Git. Inject them via environment variables or a vault (AWS Secrets Manager / SSM) — ties directly to the ICE AWS stack.

Fat JAR and spring-boot-maven-plugin?

Easycore▼

📌 Revision keywords

  • Main-Class: JarLauncher
  • java -jar app.jar
  • spring
  • boot
  • Docker

The spring-boot-maven-plugin repackages your app + all its dependencies into a single executable ("fat"/"uber") JAR. The manifest's Main-Class is Boot's JarLauncher, which sets up a nested-jar classloader and then calls your real main class.

How to build & run

mvn clean package
java -jar target/app.jar

Why it matters

  • One artifact, no external servlet container to install — perfect for Docker / Kubernetes / ECS.
  • Layered jars: the plugin can split dependencies vs app code into Docker layers so rebuilds are faster and images cache better.

Dockerfile snippet

FROM eclipse-temurin:17-jre
COPY target/app.jar app.jar
ENTRYPOINT ["java","-jar","/app.jar"]

How does auto-configuration work?

Mediumcore▼

📌 Revision keywords

  • ConditionalOnClass
  • ConditionalOnMissingBean
  • ConditionalOnProperty
  • spring
  • boot

At startup, Boot reads auto-configuration classes listed in META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports (in Boot 2.7+; older versions used spring.factories). Each class is guarded by conditions so it only applies when it makes sense:

  • @ConditionalOnClass — a class is on the classpath
  • @ConditionalOnMissingBean — you haven't already defined that bean (so your bean always wins)
  • @ConditionalOnProperty — a property is set
  • @ConditionalOnBean / @ConditionalOnWebApplication — other contextual checks

Concrete example

If HikariCP + a DataSource class are on the classpath, and you haven't defined your own DataSource bean, Boot auto-creates a Hikari DataSource from your spring.datasource.* properties. Define your own and @ConditionalOnMissingBean backs off.

How to debug it

Run with --debug (or set debug=true) to print the auto-configuration report — which configs matched and which didn't, and why. Great answer to "how would you find out why a bean wasn't created?"

Layered architecture in Spring Boot?

Easy⭐ VIcore▼

📌 Revision keywords

  • Controller
  • Service
  • Repository
  • Spring
  • Boot
  • HTTP
  • JPA
  • API
  • Controller (@RestController) — HTTP concerns: routing, request validation, DTO ↔ model mapping, status codes. No business logic.
  • Service (@Service) — business rules, orchestration, @Transactional boundaries.
  • Repository (@Repository) — persistence via Spring Data JPA / JDBC.

Request flow

HTTP → Controller (DTO) → Service (business + @Transactional) → Repository → DB

Golden rules

  • No DB calls in controllers; no HTTP types (HttpServletRequest) leaking into services.
  • Use DTOs at the API boundary — never expose JPA entities directly (avoids lazy-loading issues and over-exposing fields).
  • Put the @Transactional on the service, not the controller or repository.

Why it matters

Clear layering keeps the codebase testable (mock the layer below) and swappable (change DB or API without touching business rules) — exactly what a multi-tenant platform like ICE needs.

Spring MVC request flow?

Medium⭐ VIapi▼

📌 Revision keywords

  • GetMapping
  • ControllerAdvice
  • Spring
  • JSON
  1. DispatcherServlet receives request
  2. HandlerMapping finds @GetMapping method
  3. HandlerAdapter invokes controller
  4. Return value → HttpMessageConverter (Jackson) → JSON
  5. Exception → @ControllerAdvice handler

The components

  • DispatcherServlet — the front controller; every request goes through it.
  • HandlerMapping — maps URL+method to a controller method.
  • HandlerAdapter — invokes it, binding params (@PathVariable, @RequestBody).
  • HttpMessageConverter — Jackson turns the return value into JSON (and body into a DTO).

Filters vs Interceptors

Filters run before the DispatcherServlet (servlet level — auth, CORS, logging). Interceptors (HandlerInterceptor) run inside MVC, around the handler — good for adding a correlation ID to the MDC.

@RestController vs @Controller?

Easy⭐ VIapi▼

📌 Revision keywords

  • RestController
  • Controller
  • ResponseBody
  • JSON
  • XML

@RestController = @Controller + @ResponseBody on every method — return type serialized to JSON/XML.

@Controller — typically returns view name for Thymeleaf; use @ResponseBody per method for APIs.

Content negotiation

Jackson produces JSON by default; add the right converter and the client's Accept header decides JSON vs XML. @RestController applies @ResponseBody to all methods so you don't repeat it.

Rule of thumb

REST/JSON APIs → @RestController. Server-rendered HTML pages (Thymeleaf) → @Controller returning a view name.

How do you design a REST controller for reports?

Medium⭐ VIapi▼

📌 Revision keywords

  • GET /api/v1/reports/{id}
  • POST /api/v1/reports
  • ?page=0&size=20
  • {"code","message","fieldErrors"}
  • REST
  • api
  • JPA
  • SQL
  • Resource-oriented URLs: GET /api/v1/reports/{id}, POST /api/v1/reports
  • Request/response DTOs — never expose JPA entities
  • Pagination: ?page=0&size=20
  • Consistent error body: {"code","message","fieldErrors"}
  • OpenAPI for contract with frontend

Map Vodafone pattern: controller thin, service owns SQL tuning and business rules.

Example

@RestController
@RequestMapping("/api/v1/reports")
public class ReportController {
  private final ReportService service;

  @GetMapping("/{id}")
  public ReportDto get(@PathVariable Long id) { return service.get(id); }

  @GetMapping
  public Page<ReportDto> list(Pageable pageable) { return service.list(pageable); }

  @PostMapping
  @ResponseStatus(HttpStatus.CREATED)
  public ReportDto create(@Valid @RequestBody CreateReportRequest req) {
    return service.create(req);
  }
}

Controller stays thin; the service owns the SQL tuning and business rules (your Vodafone pattern).

Which HTTP status codes should you use?

  • 400

@Valid and Bean Validation on DTOs?

Medium⭐ VIapi▼

📌 Revision keywords

  • NotBlank
  • NotNull
  • Size
  • Email
  • MethodArgumentNotValidException
  • ControllerAdvice

Annotate DTO: @NotBlank, @NotNull, @Size, @Email. Controller: @Valid @RequestBody CreateReportRequest req.

On failure → MethodArgumentNotValidException → handle in @ControllerAdvice → 400 with per-field messages.

Example

When do you use ResponseEntity?

Mediumapi▼

📌 Revision keywords

  • 201 Created
  • Location
  • 304
  • ResponseStatus(HttpStatus.CREATED)

When you need control over status code, headers, or body together — e.g. 201 Created with Location header, or conditional 304.

Simple cases: return DTO + @ResponseStatus(HttpStatus.CREATED) is enough.

Example

@PostMapping
public ResponseEntity<ReportDto> create(@Valid @RequestBody CreateReportRequest req) {
  ReportDto dto = service.create(req);
  URI location = URI.create("/api/v1/reports/" + dto.id());
  return ResponseEntity.created(location).body(dto);   // 201 + Location header
}

Reach for ResponseEntity when status/headers vary at runtime; for the common case, returning the DTO + @ResponseStatus is cleaner.

@ControllerAdvice for global exception handling?

Medium⭐ VIapi▼

📌 Revision keywords

  • ExceptionHandler
  • EntityNotFoundException
  • AccessDeniedException
  • JSON

One class with @ExceptionHandler methods for EntityNotFoundException, validation errors, AccessDeniedException. Returns consistent JSON error schema — clients never see raw stack traces.

Example

@RestControllerAdvice
public class GlobalExceptionHandler {

  @ExceptionHandler(EntityNotFoundException.class)
  @ResponseStatus(HttpStatus.NOT_FOUND)
  public ApiError notFound(EntityNotFoundException ex) {
    return new ApiError("NOT_FOUND", ex.getMessage());
  }

  @ExceptionHandler(MethodArgumentNotValidException.class)
  @ResponseStatus(HttpStatus.BAD_REQUEST)
  public ApiError invalid(MethodArgumentNotValidException ex) {
    // map ex.getBindingResult().getFieldErrors() → field messages
    return new ApiError("VALIDATION", "Invalid request");
  }
}

One consistent error schema across the whole API; clients never see stack traces. Log the full exception server-side with the correlation ID.

DTO vs Entity — why separate?

Easy⭐ VIapi▼

📌 Revision keywords

  • API
  • JSON
  • Hide internal fields (passwords, lazy relations)
  • Stable API contract when DB schema changes
  • Avoid Jackson serializing Hibernate proxies (lazy load in JSON = disaster)
  • Validation annotations on API layer only

Mapping

Map between them with a simple mapper method or a library like MapStruct (compile-time, fast). Keep the mapping in the service layer.

ReportDto toDto(Report e) {
  return new ReportDto(e.getId(), e.getName());
}

Bonus interview point: separate request and response DTOs — you rarely accept the same fields you return (e.g. never accept id/createdAt on create).

How do you configure CORS?

Mediumapi▼

📌 Revision keywords

  • Access-Control-Allow-Origin
  • CrossOrigin
  • WebMvcConfigurer.addCorsMappings
  • *
  • Boot

Browser blocks cross-origin calls unless server sends Access-Control-Allow-Origin. In Boot: @CrossOrigin on controller or WebMvcConfigurer.addCorsMappings — whitelist origins in prod, not * with credentials.

Example (global config)

@Configuration
public class CorsConfig implements WebMvcConfigurer {
  @Override
  public void addCorsMappings(CorsRegistry registry) {
    registry.addMapping("/api/**")
        .allowedOrigins("https://app.example.com")  // not "*" with credentials
        .allowedMethods("GET","POST","PUT","DELETE")
        .allowCredentials(true);
  }
}

CORS is enforced by the browser, not the server — it's not a security boundary, just a same-origin relaxation. With Spring Security, register a CorsConfigurationSource so CORS runs before auth.

How does JSON serialization work?

Easyapi▼

📌 Revision keywords

  • JsonIgnore
  • JsonProperty
  • JavaTimeModule
  • LocalDateTime
  • JSON

Jackson on classpath (via starter-web) maps objects to JSON. Customize with @JsonIgnore, @JsonProperty, JavaTimeModule for LocalDateTime. Dates as ISO-8601 strings, not timestamps, for APIs.

API versioning strategies?

Mediumapi▼

📌 Revision keywords

  • /api/v1/reports
  • Accept: application/vnd.company.v2+json
  • API
  • json
  • Query param
  • URL path: /api/v1/reports — clearest, common at Amdocs
  • Header: Accept: application/vnd.company.v2+json
  • Query param — less RESTful

Deprecate v1 with Sunset header before removal.

Trade-offs

  • URL path (/v1/) — simplest, cache/proxy friendly, very visible. Most common.
  • Header / media type — keeps URLs clean but harder to test in a browser.
  • Query param — easy but least RESTful.

Whatever you pick: version from day one, support N-1, and announce removal with a Sunset header / deprecation notice. Internally, treat events the same way (versioned schemas).

How do you make POST idempotent?

Hardapi▼

📌 Revision keywords

  • Idempotency-Key
  • idempotent

Client sends Idempotency-Key header; server stores key + response in Redis/DB for 24h. Duplicate key returns same response without re-processing payment/report generation.

Critical for retries from mobile apps and message consumers.

Flow

  1. Client sends a unique Idempotency-Key header.
  2. Server checks a store (Redis/DB) for that key.
  3. New key → process, save key + response. Existing key → return the saved response, skip re-processing.

Back it with a unique constraint on the key so two concurrent requests can't both insert. This is essential for payment/order endpoints and for Kafka/SQS consumers (at-least-once delivery means duplicates). Ties to the Optima retry/dedup work on your resume.

JPA vs JdbcTemplate / native SQL?

Medium⭐ VIjpa▼

📌 Revision keywords

  • JPA
  • JdbcTemplate/native
  • SQL

JPA — ORM, entities, repositories, good for CRUD and object graphs. JdbcTemplate/native — full SQL control for reports, bulk updates, complex joins you tuned at Vodafone.

Hybrid is normal: JPA for writes, native query for heavy read/report paths.

What JPA gives you

A persistence context (1st-level cache) with dirty checking — change a managed entity inside a transaction and Hibernate auto-generates the UPDATE on flush; no manual SQL.

Example — native query for a report

@Query(value = "SELECT account_id, SUM(amount) total " +
               "FROM orders WHERE created_at >= :from GROUP BY account_id",
       nativeQuery = true)
List<AccountTotal> totalsSince(@Param("from") LocalDate from);

Rule of thumb: JPA for the object-graph write path, native SQL/JdbcTemplate for heavy aggregate reports where you want full control of the query plan.

What is @Entity?

Easyjpa▼

📌 Revision keywords

  • Id
  • GeneratedValue
  • Column
  • JPA
  • SQL

Marks class mapped to table. @Id + @GeneratedValue for PK. @Column for name/nullable. Hibernate implements JPA spec — generates SQL on persist/merge/find.

Example

@Entity
@Table(name = "reports")
public class Report {
  @Id
  @GeneratedValue(strategy = GenerationType.IDENTITY)
  private Long id;

  @Column(nullable = false, length = 120)
  private String name;
}

Gotchas

  • Needs a no-arg constructor (Hibernate instantiates via reflection).
  • Be careful with equals()/hashCode() on entities — base them on a business key, not the generated id (which is null before persist).
  • IDENTITY vs SEQUENCE: sequence allows JDBC batch inserts; identity disables them.

What is JpaRepository?

Easy⭐ VIjpa▼

📌 Revision keywords

  • CrudRepository
  • PagingAndSortingRepository
  • save
  • findById
  • delete
  • findByAccountIdAndStatus
  • Query
  • SQL

Extends CrudRepository, PagingAndSortingRepository. Gives save, findById, delete, derived queries findByAccountIdAndStatus, @Query for JPQL/native SQL.

Three ways to query

// 1) derived query (method name → SQL)
List<Report> findByAccountIdAndStatus(Long accountId, Status status);

// 2) JPQL
@Query("select r from Report r where r.name like %:q%")
List<Report> search(@Param("q") String q);

// 3) projection (only the columns you need → fast)
interface NameOnly { String getName(); }
List<NameOnly> findBy();

Spring generates the implementation at startup from the interface. Use projections/DTOs for read-heavy endpoints so you don't hydrate full entities.

@Transactional — how does it work and what are pitfalls?

Medium⭐ VIjpa▼

📌 Revision keywords

  • readOnly=true
  • Pitfalls:
  • Transactional

AOP proxy starts transaction on method entry, commits on success, rolls back on unchecked exceptions. readOnly=true hints DB for read-only queries.

Pitfalls: self-invocation bypasses proxy; checked exceptions don't roll back unless configured; long transactions hold DB connections.

Defaults worth knowing

  • Propagation REQUIRED (join existing tx or start one).
  • Rolls back on unchecked (RuntimeException) only — add rollbackFor = Exception.class for checked.
  • Default isolation = the DB's default (usually READ_COMMITTED).

Example

@Transactional
public void placeOrder(OrderRequest req) {
  Order o = repo.save(toEntity(req));   // dirty-checked, committed at method end
  payment.charge(o);                    // if this throws → rollback
}

Keep transactions short — never call a slow external API while holding one (it pins a DB connection).

Why does self-invocation break @Transactional?

Hard⭐ VIjpa▼

📌 Revision keywords

  • this.otherMethod()
  • Service
  • Lazy
  • Transactional
  • Spring

External call goes through Spring proxy; internal this.otherMethod() does not — no transaction advice applied. Fix: move method to another @Service or inject self interface with @Lazy.

The trap

@Service
public class OrderService {
  public void process() {
    save();   // ❌ this.save() — bypasses the proxy, NO transaction
  }
  @Transactional
  public void save() { ... }
}

Fixes

  • Move save() into a separate bean and inject it (call goes through its proxy).
  • Self-inject (@Autowired @Lazy OrderService self;) and call self.save().

Same applies to @Async, @Cacheable — any proxy-based annotation only works on calls that cross the proxy boundary.

N+1 problem and how do you fix it?

Medium⭐ VIjpa▼

📌 Revision keywords

  • EntityGraph
  • BatchSize
  • DTO projection query

Problem

Load 100 orders (1 query), then lazy-load items per order (100 queries).

Fixes

  • JOIN FETCH in JPQL
  • @EntityGraph on repository method
  • DTO projection query — only columns needed
  • @BatchSize on collection

JOIN FETCH example

@Query("select o from Order o join fetch o.items where o.accountId = :id")
List<Order> findWithItems(@Param("id") Long id);   // 1 query, not N+1

How to detect it

Turn on SQL logging (spring.jpa.show-sql=true or org.hibernate.SQL=DEBUG) and watch for a burst of identical SELECTs. Hibernate statistics / a tool like p6spy also surfaces it.

Pick the fix by use case: JOIN FETCH/@EntityGraph for a single request, @BatchSize to reduce N queries to N/batch, DTO projection when you only need a few columns.

FetchType LAZY vs EAGER?

Mediumjpa▼

📌 Revision keywords

  • LAZY
  • EAGER

LAZY — load association when accessed (default collections). EAGER — always join/load — can explode result set. Prefer LAZY + explicit fetch in query for list endpoints.

The classic error

Accessing a LAZY association after the transaction/session closed throws LazyInitializationException ("no Session"). It often appears when Jackson serializes an entity outside the service layer — another reason to return DTOs.

Fixes

  • Fetch what you need inside the transaction (JOIN FETCH / @EntityGraph).
  • Map to a DTO before returning.
  • Avoid the anti-pattern of open-session-in-view (on by default in Boot — consider disabling it).

HikariCP connection pool tuning?

Medium⭐ VIjpa▼

📌 Revision keywords

  • spring.datasource.hikari.maximum-pool-size
  • connection-timeout
  • max-lifetime
  • spring

spring.datasource.hikari.maximum-pool-size (often 10–30), connection-timeout, max-lifetime. Pool size ≈ concurrent DB-bound threads. Too small → threads block; too large → DB overload.

Monitor active/idle connections via Actuator metrics.

Sizing it

A common starting formula: pool size ≈ ((core_count * 2) + effective_spindles), then validate under load. Bigger is not better — too many connections overwhelm the DB. Match the pool to what the DB can actually handle across all service instances.

spring.datasource.hikari.maximum-pool-size: 20
spring.datasource.hikari.connection-timeout: 30000   # ms to wait for a conn
spring.datasource.hikari.max-lifetime: 1800000       # recycle before DB idle-kill

Expose Hikari metrics via Actuator/Micrometer (hikaricp.connections.active) so you can alert before exhaustion.

@Version optimistic locking?

Hardjpa▼

📌 Revision keywords

  • Version Long version
  • WHERE version = ?
  • OptimisticLockingFailureException

Entity has @Version Long version. UPDATE includes WHERE version = ?; if 0 rows updated → OptimisticLockingFailureException. Prevents lost updates when two users edit same report row.

Optimistic vs pessimistic

  • Optimistic (@Version) — no DB lock; detect the conflict at commit. Best for low-contention web edits.
  • Pessimistic (SELECT ... FOR UPDATE via @Lock(PESSIMISTIC_WRITE)) — locks the row up front. Use for high-contention hotspots (inventory, balances).

Handling the failure

Catch OptimisticLockingFailureException and either retry the transaction or return 409 Conflict so the user re-loads and re-applies their change. Prevents the lost-update problem when two users edit the same row.

JPA cascade types — what is risky?

Hardjpa▼

📌 Revision keywords

  • CascadeType.ALL
  • PERSIST
  • REMOVE
  • JPA

CascadeType.ALL on parent→children can accidentally persist/delete entire graph. Use explicit PERSIST/REMOVE only where business requires. OrphanRemoval deletes children when removed from collection — understand before enabling.

The cascade types

  • PERSIST, MERGE, REMOVE, REFRESH, DETACH, and ALL (all of them).

Why ALL is risky

@OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true)
private List<OrderItem> items;

With ALL + orphanRemoval, deleting an order (or just removing an item from the list) cascades deletes you may not intend, and can fire a flood of DELETEs. Prefer declaring only the specific cascades the relationship actually needs.

Connection pool exhausted — causes?

Hard⭐ VIjpa▼

📌 Revision keywords

  • Transactional
  • API
  • Not closing streams (try
  • Long @Transactional methods (external API inside tx)
  • Not closing streams (try-with-resources)
  • Leak detection: enable Hikari leak detection threshold in dev
  • Thread dump + metrics: all connections in use

How to diagnose

  1. Symptom: requests hang then fail with "Connection is not available, request timed out".
  2. Enable Hikari leak-detection-threshold (e.g. 20000 ms) — it logs the stack trace of the borrower that held a connection too long.
  3. Check Actuator metrics: hikaricp.connections.active pinned at max.
  4. Take a thread dump to see where threads are parked.

Common causes & fixes

  • Slow external call inside @Transactional → move it outside the tx.
  • Streaming results without closing the stream → use try-with-resources.
  • Pool simply too small for load → size it and add timeouts.

REQUIRES_NEW transaction propagation?

Hardjpa▼

📌 Revision keywords

  • In simple terms:
  • REQUIRES_NEW transaction propagation
  • Suspends current transaction, opens new one — commits independently.
  • Use for audit log that must persist even if main business transaction rolls back.
  • Overuse hurts performance and debugging.

The main propagation modes

  • REQUIRED (default) — join the caller's tx or start one.
  • REQUIRES_NEW — suspend the caller's tx, run in a brand-new independent tx.
  • NESTED — savepoint inside the current tx.
  • SUPPORTS / NOT_SUPPORTED / MANDATORY / NEVER — situational.

Example — audit that must survive a rollback

@Transactional(propagation = Propagation.REQUIRES_NEW)
public void writeAudit(AuditEvent e) { auditRepo.save(e); }

Caveat: REQUIRES_NEW uses a second DB connection while the first is suspended — overuse can deadlock or exhaust the pool.

Security filter chain order?

Medium⭐ VIsecurity▼

📌 Revision keywords

  • SecurityFilterChain
  • JWT

Filters run before DispatcherServlet: security context restoration → JWT/OAuth filter → authorization → controller. SecurityFilterChain bean defines which URLs are permitAll vs authenticated.

Example config

@Bean
SecurityFilterChain chain(HttpSecurity http) throws Exception {
  return http
    .csrf(csrf -> csrf.disable())                       // stateless API
    .sessionManagement(s -> s.sessionCreationPolicy(STATELESS))
    .authorizeHttpRequests(auth -> auth
        .requestMatchers("/actuator/health", "/auth/**").permitAll()
        .anyRequest().authenticated())
    .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()))
    .build();
}

The chain is an ordered list of servlet filters. A custom filter (e.g. JWT) is added with addFilterBefore(...) relative to UsernamePasswordAuthenticationFilter. The result of authentication lands in the SecurityContextHolder.

Stateless JWT authentication flow?

Medium⭐ VIsecurity▼

📌 Revision keywords

  • Authorization: Bearer <token>
  • JWT
  • No server session
  1. Login → server validates credentials → issues signed JWT
  2. Client sends Authorization: Bearer <token>
  3. Filter validates signature/expiry, builds Authentication
  4. No server session — scale horizontally

Refresh tokens for long-lived mobile apps; short access token TTL.

What's inside a JWT

Three Base64 parts: header (alg) . payload (claims: sub, roles, exp) . signature. The server only needs to verify the signature — no DB lookup — which is why it scales.

Trade-offs & gotchas

  • You can't easily revoke a JWT before expiry → keep access-token TTL short (5–15 min) + refresh tokens.
  • Never put secrets/PII in the payload (it's only encoded, not encrypted).
  • Validate exp, iss, aud; use asymmetric (RS256) so only the IdP can sign.

OAuth2 resource server?

CSRF for REST APIs?

Easysecurity▼

📌 Revision keywords

  • REST
  • JWT
  • CSRF protects cookie-based browser sessions.
  • Stateless JWT in Authorization header → typically disable CSRF for pure APIs.
  • If using session cookies + SPA, enable CSRF token.

Why

CSRF attacks ride on credentials the browser sends automatically — i.e. cookies. A token in the Authorization header is not sent automatically, so a pure token API isn't CSRF-vulnerable and CSRF is typically disabled.

When to keep it on

If your SPA authenticates with a session cookie, keep CSRF enabled and use the cookie-based token repository (CookieCsrfTokenRepository.withHttpOnlyFalse()) so the SPA can echo the token in a header.

401 vs 403?

Easysecurity▼

📌 Revision keywords

  • 401 Unauthorized
  • 403 Forbidden
  • API

401 Unauthorized — not authenticated (missing/invalid token). 403 Forbidden — authenticated but lacks permission. Wrong status confuses API clients and security audits.

Quick rule

401 Unauthorized  → "I don't know who you are"  (authenticate first)
403 Forbidden     → "I know you, but you can't"  (re-auth won't help)

In Spring Security these map to the AuthenticationEntryPoint (401) and AccessDeniedHandler (403). Returning the right one matters for clients (whether to retry login) and for security audits.

Liveness vs readiness probes?

Medium⭐ VIactuator▼

📌 Revision keywords

  • /actuator/health/liveness
  • readiness
  • Liveness
  • Boot
  • Liveness — process up? Restart pod if fails.
  • Readiness — can accept traffic? DB/upstream OK? Remove from load balancer if fails.

K8s: /actuator/health/liveness and readiness (Boot 2.3+ probes).

Why the distinction matters

Kubernetes acts differently on each: a failed liveness probe restarts the pod; a failed readiness probe just removes it from the Service (no traffic) until it recovers.

management.endpoint.health.probes.enabled: true
management.endpoint.health.group.readiness.include: db,redis,kafka

Common pitfall

Don't put external-dependency checks (DB/Kafka) in liveness — a transient DB blip would restart-loop every pod. External deps belong in readiness; liveness should only mean "the JVM/process is healthy."

Graceful shutdown?

Medium⭐ VIactuator▼

📌 Revision keywords

  • server.shutdown=graceful
  • terminationGracePeriodSeconds

server.shutdown=graceful — stop accepting new requests, finish in-flight, then close context. K8s preStop hook + adequate terminationGracePeriodSeconds.

Config

server.shutdown: graceful
spring.lifecycle.timeout-per-shutdown-phase: 30s

How it works with K8s

  1. K8s sends SIGTERM and stops routing new traffic (after the pod is marked not-ready).
  2. Boot stops accepting new requests but lets in-flight ones finish (up to the timeout).
  3. A preStop sleep + adequate terminationGracePeriodSeconds avoids dropping requests during the rollout.

Without this, a rolling deploy can return 5xx to users mid-request — a common cause of "errors only during deploys."

JVM flags for Spring Boot in containers?

📌 Revision keywords

  • JVM
  • Spring
  • Boot

-XX:MaxRAMPercentage=75.0 respects cgroup memory limit. Container-aware ergonomics in Java 11+. Avoid fixed huge -Xmx exceeding pod limit → OOMKilled.

Container-aware flags

-XX:MaxRAMPercentage=75.0          # heap as % of the cgroup limit
-XX:InitialRAMPercentage=50.0

Key idea

What is @MockBean?

Medium⭐ VItesting▼

📌 Revision keywords

  • WebMvcTest
  • Spring
  • Mockito
  • JSON

Replaces bean in Spring test context with Mockito mock — use in @WebMvcTest to mock service layer when testing controller mappings and JSON responses.

Example

@WebMvcTest(ReportController.class)
class ReportControllerTest {
  @Autowired MockMvc mvc;
  @MockBean ReportService service;          // real bean replaced by a mock

  @Test void returns404() throws Exception {
    given(service.get(1L)).willThrow(new EntityNotFoundException());
    mvc.perform(get("/api/v1/reports/1"))
       .andExpect(status().isNotFound());
  }
}

@MockBean swaps a bean in the Spring test context with a Mockito mock so you can test one layer in isolation. Note: in Spring Boot 3.4+ it's being superseded by @MockitoBean. A plain @Mock (Mockito) is for pure unit tests with no context.

Testcontainers vs H2?

Medium⭐ VItesting▼

📌 Revision keywords

  • SQL
  • Docker
  • H2 fast but different SQL dialect from Oracle/PostgreSQL prod.
  • Testcontainers spins real DB in Docker — catches migration and query issues.
  • Worth it for repository integration tests.

Example

@SpringBootTest
@Testcontainers
class ReportRepositoryIT {
  @Container
  static PostgreSQLContainer<?> pg = new PostgreSQLContainer<>("postgres:16");

  @DynamicPropertySource
  static void props(DynamicPropertyRegistry r) {
    r.add("spring.datasource.url", pg::getJdbcUrl);
    r.add("spring.datasource.username", pg::getUsername);
    r.add("spring.datasource.password", pg::getPassword);
  }
}

H2 is fast but its SQL dialect differs from Postgres/Oracle — it hides dialect-specific bugs, Flyway migration issues, and JSON/window-function behavior. Testcontainers runs the real DB in Docker so integration tests match prod. Reuse one container across tests to keep CI fast.
