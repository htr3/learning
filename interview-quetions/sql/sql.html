How do you use EXPLAIN to tune a slow query?

Medium⭐ VITuning▼

📌 Revision keywords

  • EXPLAIN ANALYZE
  • EXPLAIN FORMAT=JSON
  • type
  • key
  • rows
  • Extra
  • JSON

Run EXPLAIN ANALYZE (or EXPLAIN FORMAT=JSON), look for full table scans, high rows examined, filesort, temporary tables, bad join order — then index or rewrite.

Detailed explanation

MySQL: check type (ALL vs range vs ref), key, rows, Extra (Using filesort). Compare before/after row counts and actual time. Validate on prod-like data volume, not empty dev DB.

Example

EXPLAIN SELECT r.* FROM report_fact r
JOIN account a ON r.account_id = a.id
WHERE r.report_date BETWEEN '2025-01-01' AND '2025-01-31'
  AND a.region = 'DE';
-- Add: INDEX idx_report_date_account (report_date, account_id)

From your experience

Vodafone Germany reporting: EXPLAIN showed full scans on date filters — composite indexes + join rewrite → report time >10% faster, lower peak CPU.

Follow-ups

Covering index? Index includes all SELECT columns — avoids table lookup.

Reading it well

Compare estimated vs actual rows — a big gap means stale statistics (run ANALYZE TABLE). Note: EXPLAIN ANALYZE executes the query, so be careful with writes. An index-only / covering scan ("Using index") is ideal — no table lookup.

B-tree indexes, composite indexes, and leftmost prefix rule

Medium⭐ VIIndexes▼

📌 Revision keywords

  • (a, b, c)
  • a
  • a,b
  • b
  • (report_date, account_id)
  • (customer_id, created_at) for customer + date queries
  • Column order matters

Composite index (a, b, c) helps queries filtering on a, or a,b, not usually on b alone. Order columns by selectivity and equality-before-range.

Detailed explanation

Too many indexes slow writes. Duplicate/redundant indexes waste space. For reporting: often (report_date, account_id) matches WHERE + JOIN. Avoid indexing low-cardinality alone unless combined.

Example

CREATE INDEX idx_fact_date_acct ON report_fact (report_date, account_id);

From your experience

XL Axiata: indexing on hot lookup keys cut response ~10% and reduced fallouts from timeouts.

Follow-ups

When not to index? Small tables, heavy write tables with rare reads, columns updated constantly.

Covering index

If an index contains every column the query needs (filter + select), the DB answers from the index alone — an "index-only scan". Watch for redundant indexes (a prefix of another) and remember each index adds write/maintenance cost.

INNER vs LEFT JOIN — practical difference?

EasyBasics▼

📌 Revision keywords

  • In simple terms:
  • trade-offs
  • Find orphans: LEFT JOIN + WHERE right.id IS NULL
  • WHERE on right can act like INNER
  • INNER keeps only matching rows both sides.
  • LEFT keeps all left rows; NULLs on right when no match — useful for optional dimensions but can hide data issues if not intended.

Example

-- Reports only for accounts that exist
SELECT * FROM report_fact r
INNER JOIN account a ON r.account_id = a.id;

-- All accounts even without reports this month
SELECT * FROM account a
LEFT JOIN report_fact r ON a.id = r.account_id AND r.report_date = CURDATE();

Follow-ups

LEFT JOIN + WHERE on right table turns into INNER effectively — filter in ON vs WHERE carefully.

How the DB executes a join

Optimizer picks nested-loop (good with an index on the inner table), hash join (large unindexed sets), or merge join (pre-sorted). Make sure join keys are indexed and of the same type — a type mismatch silently disables index use.

Normalization vs denormalization for reporting

EasyDesign▼

📌 Revision keywords

  • In simple terms:
  • trade-offs
  • OLTP: normalize (3NF) to reduce redundancy.
  • Reporting: often denormalized fact tables or materialized summaries for read performance.

Detailed explanation

Telecom reporting may use star schema: fact (usage, charges) + dimensions (account, product). ETL nightly populates facts — trades storage for fast dashboards.

From your experience

Vodafone reporting paths hit pre-aggregated tables where possible instead of joining 10 OLTP tables live.

Practical rule

Keep the source of truth normalized (3NF) for integrity; denormalize only for read paths via summary/materialized tables refreshed by ETL or triggers. State the refresh/staleness trade-off — that's what interviewers probe.

ACID and isolation levels — what breaks at each level?

MediumTransactions▼

📌 Revision keywords

  • ACID
  • READ UNCOMMITTED: dirty reads.
  • READ COMMITTED: non-repeatable reads.
  • REPEATABLE READ (MySQL InnoDB default): phantoms possible.
  • SERIALIZABLE: safest, slowest.

Detailed explanation

Long-running report in REPEATABLE READ may hold gap locks — impacts writes. Use read-only replica or snapshot isolation for heavy analytics off primary OLTP.

Follow-ups

Deadlock? InnoDB picks victim — retry with backoff; keep transactions short.

MVCC & setting it

InnoDB uses MVCC so reads don't block writes (consistent snapshot). Set per transaction with SET TRANSACTION ISOLATION LEVEL READ COMMITTED;. Higher isolation = more locking/blocking — pick the lowest level that's correct for the use case.

OFFSET vs keyset pagination for large tables

MediumAPI▼

📌 Revision keywords

  • LIMIT 100000, 50
  • WHERE id > :lastId ORDER BY id LIMIT 50

LIMIT 100000, 50 scans/skips 100k rows — slow. Keyset: WHERE id > :lastId ORDER BY id LIMIT 50 uses index.

Example

SELECT * FROM subscriber_event
WHERE id > :cursor
ORDER BY id
LIMIT 50;

Follow-ups

Multi-column sort cursor? Encode (created_at, id) tuple in opaque cursor token.

One more OFFSET pitfall

Beyond being slow, OFFSET can skip or duplicate rows when data is inserted/deleted between page loads. Keyset (cursor) pagination is stable because it anchors on the last seen key.

N+1 query problem — how do you fix it in apps?

MediumORM▼

📌 Revision keywords

  • SQL
  • Spring
  • JPA
  • One query loads parents, then N queries for children.
  • Fix: JOIN fetch, batch IN query, or single SQL with aggregation.

Example

-- Bad: loop accounts, query reports each time
-- Good:
SELECT * FROM report_fact WHERE account_id IN (...);

From your experience

Spring/JPA paths for reporting preferred explicit SQL over lazy collections — predictable performance under load.

Detecting it

Log the SQL count per request (Hibernate statistics / a query counter) — a burst of identical SELECTs is the tell. Fixes: JOIN FETCH/@EntityGraph, a batched IN (...) query, or a DTO projection that selects only what you need.

Row locks, gap locks, and hot-row contention

HardInnoDB▼

📌 Revision keywords

  • INSERT ... ON DUPLICATE KEY UPDATE
  • SELECT FOR UPDATE

Updates on same index range serialize. High-contention counters: avoid updating single row — shard counters or use atomic INSERT ... ON DUPLICATE KEY UPDATE per bucket.

Detailed explanation

Integration fallout queues sometimes hammer one status row — spread by partition key or batch status updates.

Follow-ups

SELECT FOR UPDATE in reporting job? Hold locks minimal time; prefer MVCC read without lock for pure reads.

Diagnosing & recovering

Inspect with SHOW ENGINE INNODB STATUS (latest deadlock) and performance_schema. On deadlock, InnoDB rolls back one victim — the app should retry with backoff. Keep transactions short and touch rows in a consistent order to avoid cycles.

Safe production lookups by MIN / accountId (Subscriber Tool angle)

Medium⭐ VIProduction▼

📌 Revision keywords

  • LIKE '%...%'
  • SQL

Read-only DB user, indexed equality lookups only, query timeout, audit log, optional read replica — no ad-hoc wildcard SQL on prod.

Detailed explanation

Telecom IDs (MIN, MSISDN, accountId) need exact match indexes. Reject LIKE '%...%' patterns that scan millions of subscribers.

Example

SELECT col1, col2 FROM subscriber
WHERE account_id = :id
LIMIT 1;
-- max_execution_time = 5000

From your experience

Built Subscriber Tool at Optima so support stops writing risky manual SQL — same principles apply in interviews as production maturity.

Safety details

Always use parameterized queries (never string-concat user input — SQL injection). Combine: read-only role, statement timeout, row LIMIT, audit logging, and a read replica so support tooling can't impact the OLTP primary.

Aggregations and window functions for reporting

HardAnalytics▼

📌 Revision keywords

  • GROUP BY
  • ROW_NUMBER
  • SUM() OVER

GROUP BY for totals; window functions (ROW_NUMBER, SUM() OVER) for rankings and running totals without self-joins.

Example

SELECT account_id, report_date, revenue,
  SUM(revenue) OVER (PARTITION BY account_id ORDER BY report_date) AS running_total
FROM report_fact;

Follow-ups

MySQL 8+ window support — confirm version in interview; mention alternative subqueries on older DBs.

Window vs GROUP BY

GROUP BY collapses rows; a window function keeps every row and adds a computed column. Control the window with a frame: ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW for running totals, or PARTITION BY + ROW_NUMBER() for "top-N per group".

WHERE vs GROUP BY vs HAVING — order of execution?

Medium⭐ VISQL▼

📌 Revision keywords

  • COUNT(*) > 5
  • WHERE
  • GROUP BY
  • HAVING

WHERE filters rows before grouping. GROUP BY aggregates. HAVING filters groups after aggregation.

SELECT dept, COUNT(*) AS cnt FROM employees
WHERE active = 1
GROUP BY dept
HAVING COUNT(*) > 5;

Common mistake: putting aggregate condition in WHERE — use HAVING for COUNT(*) > 5.

Logical execution order

FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT

That's why a column alias defined in SELECT can't be used in WHERE (SELECT runs later) but can be used in ORDER BY.

UNION vs UNION ALL?

EasySQL▼

📌 Revision keywords

  • UNION
  • UNION ALL
  • Faster than UNION
  • Columns must align in count/type

UNION merges two result sets and removes duplicate rows (extra sort/distinct cost). UNION ALL keeps duplicates — faster when you know sets don't overlap (e.g. Jan sales UNION ALL Feb sales).

Details

Column names/aliases come from the first SELECT; a single ORDER BY at the end sorts the combined result. Prefer UNION ALL unless you specifically need de-duplication (which forces an extra sort/distinct pass).

DELETE vs TRUNCATE vs DROP?

MediumSQL▼

📌 Revision keywords

  • DELETE
  • TRUNCATE
  • DROP
  • DELETE — row-level, can use WHERE, triggers fire, rollback possible
  • TRUNCATE — all rows fast, resets auto-increment, minimal logging
  • DROP — removes table structure and data entirely

In prod telecom DBs: never TRUNCATE without change ticket — billing tables are sensitive.

More gotchas

  • TRUNCATE can't have a WHERE, doesn't fire row triggers, and (in MySQL) auto-commits — not easily rolled back.
  • TRUNCATE is blocked if other tables have FKs referencing the table.
  • For huge DELETEs, batch in chunks to avoid long locks and replication lag.

What is a correlated subquery?

Medium⭐ VISQL▼

📌 Revision keywords

  • In simple terms:
  • a correlated subquery
  • Inner query references outer query row — runs per outer row (can be slow).
  • Example: customers who placed an order in last 30 days.
SELECT c.name FROM customers c
WHERE EXISTS (
  SELECT 1 FROM orders o
  WHERE o.customer_id = c.id AND o.created_at > NOW() - INTERVAL 30 DAY
);

Often rewrite as JOIN for performance on large reporting tables — your Vodafone tuning experience.

The taxonomy

  • Scalar — returns one value (usable in SELECT).
  • Correlated — references the outer row, runs per row.
  • Derived table — a subquery in FROM (alias required).

For "does a related row exist?", EXISTS usually beats IN (short-circuits) and is NULL-safe unlike NOT IN.

50 Basic SQL Queries

Hands-on patterns: SELECT, JOINs, aggregates, DML, DDL, windows, and transactions. Sample tables: employees, departments, customers, orders, products.

50 queries in this section

SELECT all rows from a table

EasySELECT▼
  • Use SELECT * only for exploration; in production list columns you need
  • Reads full table — can be slow on large tables without LIMIT

📌 Revision keywords

  • SELECT * FROM employees;
SELECT * FROM employees;

Tip: In production prefer listing columns over SELECT * — schema changes won't surprise you and you transfer less data. Add LIMIT when exploring big tables.

SELECT specific columns

EasySELECT▼

📌 Revision keywords

  • In simple terms:
  • Reduces network and memory
  • Makes query intent obvious to other developers
SELECT id, name, dept, salary FROM employees;

Tip: Selecting only needed columns enables covering indexes (index-only scans) and reduces network/memory.

SELECT DISTINCT values

EasySELECT▼
  • Useful for unique departments, cities, statuses
  • DISTINCT applies to the full selected row combination

📌 Revision keywords

  • SELECT DISTINCT dept FROM employees;
SELECT DISTINCT dept FROM employees;

Tip: DISTINCT applies to the whole selected row, not one column. It sorts/hashes to dedupe — on large data a GROUP BY can be clearer and similarly costed.

WHERE — filter by equality

EasyWHERE▼

📌 Revision keywords

  • In simple terms:
  • Only rows matching the condition are returned
  • Combine with AND/OR for multiple conditions
SELECT * FROM employees WHERE dept = 'Engineering';

Tip: Equality on an indexed column is the fastest filter. Avoid wrapping the column in a function (e.g. WHERE UPPER(dept)=...) — it disables the index.

WHERE — AND / OR conditions

EasyWHERE▼

📌 Revision keywords

  • In simple terms:
  • Use parentheses when mixing AND and OR
  • AND is evaluated before OR unless grouped
SELECT * FROM employees
WHERE dept = 'Sales' AND salary > 50000
   OR (dept = 'HR' AND active = 1);

Tip: AND binds tighter than OR — always parenthesize mixed conditions to avoid logic bugs.

WHERE — IN list

EasyWHERE▼

📌 Revision keywords

  • In simple terms:
  • Cleaner than many OR conditions
  • NOT IN excludes listed values
SELECT * FROM employees WHERE dept IN ('HR', 'Finance', 'IT');

Tip: IN is cleaner than many ORs. Beware NOT IN with a list that contains NULL — it returns no rows; use NOT EXISTS instead.

WHERE — BETWEEN range

EasyWHERE▼

📌 Revision keywords

  • In simple terms:
  • Works on dates, numbers, strings
  • Use consistent date format/timezone
SELECT * FROM orders
WHERE created_at BETWEEN '2025-01-01' AND '2025-01-31';

Tip: BETWEEN is inclusive on both ends. For timestamps prefer >= start AND < next_day to avoid missing/duplicating boundary rows.

WHERE — LIKE pattern match

EasyWHERE▼

📌 Revision keywords

  • In simple terms:
  • 'A%' = starts with A
  • Leading % often prevents index use
SELECT * FROM customers WHERE name LIKE 'A%';

Tip: A leading wildcard ('%abc') can't use a normal B-tree index → full scan. For substring search use a full-text index or trigram index.

WHERE — IS NULL / IS NOT NULL

EasyWHERE▼

📌 Revision keywords

  • In simple terms:
  • Use IS NULL / IS NOT NULL
  • COALESCE gives default for NULL
SELECT * FROM employees WHERE manager_id IS NULL;
SELECT * FROM employees WHERE email IS NOT NULL;

Tip: = NULL never matches — always use IS NULL/IS NOT NULL. COALESCE(col, default) substitutes a value.

ORDER BY ascending

EasyORDER BY▼

📌 Revision keywords

  • In simple terms:
  • Apply after WHERE filter
  • Can sort by multiple columns
SELECT * FROM employees ORDER BY hire_date ASC;

Tip: Sorting is cheap when an index already provides the order; otherwise the DB does a filesort. Index (filter_col, sort_col) to serve WHERE + ORDER BY together.

ORDER BY descending (multiple columns)

EasyORDER BY▼

📌 Revision keywords

  • In simple terms:
  • Common for newest-first dates
  • Tie-break with second column
SELECT * FROM employees ORDER BY dept ASC, salary DESC;

Tip: You can mix directions per column (ORDER BY dept ASC, salary DESC). NULL ordering differs by DB — use NULLS FIRST/LAST (Postgres) when it matters.

LIMIT and OFFSET (pagination)

EasyLIMIT▼

📌 Revision keywords

  • In simple terms:
  • Page 3 size 10: LIMIT 10 OFFSET 20
  • Large OFFSET on big tables can be slow
SELECT * FROM orders ORDER BY id LIMIT 10 OFFSET 20;
-- MySQL: LIMIT offset, count → LIMIT 20, 10

Tip: Large OFFSET scans and discards all skipped rows — switch to keyset pagination (WHERE id > :last ORDER BY id LIMIT n) for deep pages.

COUNT rows

EasyAggregate▼

📌 Revision keywords

  • In simple terms:
  • COUNT(*) counts all rows
  • COUNT(col) ignores NULL in col
SELECT COUNT(*) AS total_employees FROM employees;

Tip: COUNT(*) counts rows (incl. NULLs); COUNT(col) skips NULLs; COUNT(DISTINCT col) counts uniques.

SUM — total amount

EasyAggregate▼

📌 Revision keywords

  • In simple terms:
  • NULLs ignored
  • Use with GROUP BY for per-group totals
SELECT SUM(amount) AS total_revenue FROM orders;

Tip: SUM ignores NULLs and returns NULL for an empty set — wrap with COALESCE(SUM(x), 0) if you want 0.

AVG — average salary

EasyAggregate▼

📌 Revision keywords

  • In simple terms:
  • NULLs excluded from average
  • Watch integer division in some DBs
SELECT AVG(salary) AS avg_salary FROM employees;

Tip: AVG excludes NULLs from both numerator and denominator — if you want NULLs treated as 0, AVG(COALESCE(x,0)).

MIN and MAX

EasyAggregate▼

📌 Revision keywords

  • In simple terms:
  • Works on numbers, dates, strings
  • Useful in dashboards and range checks
SELECT MIN(salary) AS min_sal, MAX(salary) AS max_sal FROM employees;

Tip: MIN/MAX work on dates and strings too, and can be answered instantly from an index on that column.

GROUP BY — count per department

EasyGROUP BY▼

📌 Revision keywords

  • In simple terms:
  • Non-aggregated SELECT cols must be in GROUP BY
  • Example: employees per department
SELECT dept, COUNT(*) AS headcount
FROM employees
GROUP BY dept;

Tip: Every non-aggregated column in SELECT must appear in GROUP BY (MySQL's ONLY_FULL_GROUP_BY enforces this).

HAVING — filter grouped results

EasyHAVING▼

📌 Revision keywords

  • In simple terms:
  • HAVING AVG(salary) > 60000 style filters
  • Use WHERE for row-level filters first
SELECT dept, AVG(salary) AS avg_sal
FROM employees
GROUP BY dept
HAVING AVG(salary) > 60000;

Tip: Put row filters in WHERE (runs before grouping = less work) and group filters in HAVING.

INNER JOIN — employees and departments

EasyJOIN▼

📌 Revision keywords

  • In simple terms:
  • No match = row dropped
  • Most common join type
SELECT e.name, d.name AS dept_name
FROM employees e
INNER JOIN departments d ON e.dept_id = d.id;

Tip: Alias tables and qualify columns (e.id, d.name) for readability and to avoid ambiguous-column errors. Index both join keys.

LEFT JOIN — all customers, even without orders

EasyJOIN▼

📌 Revision keywords

  • In simple terms:
  • Find orphans: LEFT JOIN + WHERE right.id IS NULL
  • WHERE on right can act like INNER
SELECT c.name, o.id AS order_id
FROM customers c
LEFT JOIN orders o ON c.id = o.customer_id;

Tip: To find "rows on the left with no match", use LEFT JOIN ... WHERE right.id IS NULL. Putting a right-table filter in WHERE turns a LEFT JOIN back into an INNER.

RIGHT JOIN — all orders with customer info

EasyJOIN▼

📌 Revision keywords

  • In simple terms:
  • Same NULL fill behavior as LEFT on non-matching side
  • Interview: mention LEFT is preferred
SELECT c.name, o.amount
FROM customers c
RIGHT JOIN orders o ON c.id = o.customer_id;

Tip: RIGHT JOIN is rare in practice — most teams rewrite it as a LEFT JOIN with the tables swapped for readability.

JOIN three tables

EasyJOIN▼

📌 Revision keywords

  • In simple terms:
  • Always specify ON conditions
  • Wrong join order can explode row count
SELECT c.name, o.id, p.name AS product
FROM orders o
JOIN customers c ON o.customer_id = c.id
JOIN order_items oi ON o.id = oi.order_id
JOIN products p ON oi.product_id = p.id;

Tip: The written join order doesn't fix execution order — the optimizer reorders based on stats. What matters is that every join key is indexed.

Self JOIN — employee and manager names

EasyJOIN▼

📌 Revision keywords

  • In simple terms:
  • Use aliases (e, m)
  • Common for hierarchies
SELECT e.name AS employee, m.name AS manager
FROM employees e
LEFT JOIN employees m ON e.manager_id = m.id;

Tip: A self join needs two aliases of the same table (e and m) — perfect for parent/child like employee→manager. Use LEFT JOIN so top-level rows (no manager) still show.

CROSS JOIN — every combination

EasyJOIN▼

📌 Revision keywords

  • In simple terms:
  • No ON clause
  • Accidental cross join = huge result set
SELECT e.name, d.name AS dept
FROM employees e
CROSS JOIN departments d;

Tip: CROSS JOIN produces N×M rows (Cartesian product). Usually accidental (a missing ON clause); intentional only for generating combinations/calendars.

UNION — combine two result sets (dedupe)

EasySet ops▼

📌 Revision keywords

  • In simple terms:
  • Same column count and types required
  • UNION ALL is faster when dupes OK
SELECT name FROM employees WHERE dept = 'IT'
UNION
SELECT name FROM contractors WHERE team = 'IT';

Tip: UNION removes duplicates (extra sort/distinct cost) and requires matching column counts/types across selects.

UNION ALL — keep duplicates

EasySet ops▼

📌 Revision keywords

  • In simple terms:
  • Faster than UNION
  • Columns must align in count/type
SELECT city FROM customers
UNION ALL
SELECT city FROM suppliers;

Tip: UNION ALL keeps duplicates and is faster — use it when the result sets can't overlap (e.g. month partitions).

Scalar subquery in SELECT

EasySubquery▼

📌 Revision keywords

  • In simple terms:
  • Must return one row, one column
  • Can be slow if run per row — profile it
SELECT name, salary,
  (SELECT AVG(salary) FROM employees) AS company_avg
FROM employees;

Tip: A scalar subquery in SELECT must return exactly one row/one column and runs per outer row — for large sets a JOIN or window function is usually faster.

Subquery with IN

EasySubquery▼

📌 Revision keywords

  • In simple terms:
  • Often clearer than complex JOIN
  • Watch NULL behavior in IN lists
SELECT name FROM customers
WHERE id IN (SELECT customer_id FROM orders WHERE amount > 1000);

Tip: IN (subquery) is readable, but watch NULLs with NOT IN (a single NULL makes it return nothing) — prefer NOT EXISTS.

EXISTS — customers who placed orders

EasySubquery▼

📌 Revision keywords

  • In simple terms:
  • Stops at first match
  • SELECT 1 inside EXISTS is idiomatic
SELECT name FROM customers c
WHERE EXISTS (
  SELECT 1 FROM orders o WHERE o.customer_id = c.id
);

Tip: EXISTS short-circuits on the first matching row, so it's often faster than IN for correlated existence checks.

NOT EXISTS — customers with no orders

EasySubquery▼

📌 Revision keywords

  • In simple terms:
  • Stops at first match
  • SELECT 1 inside EXISTS is idiomatic
SELECT name FROM customers c
WHERE NOT EXISTS (
  SELECT 1 FROM orders o WHERE o.customer_id = c.id
);

Tip: NOT EXISTS is the NULL-safe, index-friendly way to find "rows with no related row" (e.g. customers with no orders).

INSERT — single row

EasyDML▼

📌 Revision keywords

  • In simple terms:
  • List columns explicitly
  • Auto-increment id usually omitted
INSERT INTO employees (name, dept, salary)
VALUES ('Alice', 'Engineering', 75000);

Tip: Always list target columns explicitly so a future column reorder/addition doesn't break the insert. Use parameters, never string concatenation.

INSERT — multiple rows

EasyDML▼

📌 Revision keywords

  • In simple terms:
  • Faster than many single INSERTs
  • Watch transaction/batch size
INSERT INTO employees (name, dept, salary) VALUES
  ('Bob', 'Sales', 55000),
  ('Carol', 'HR', 48000);

Tip: One multi-row INSERT is dramatically faster than N single inserts (one round-trip, one transaction). For bulk loads use LOAD DATA / COPY.

UPDATE — change salary

EasyDML▼

📌 Revision keywords

  • In simple terms:
  • Always use WHERE in production
  • Test with SELECT first
UPDATE employees SET salary = salary * 1.05 WHERE dept = 'Engineering';

Tip: Test the WHERE as a SELECT first — an UPDATE without a WHERE rewrites every row. Wrap risky updates in a transaction.

UPDATE with JOIN (MySQL)

EasyDML▼

📌 Revision keywords

  • In simple terms:
  • Powerful — easy to mis-update rows
  • Use transaction; check rows affected
UPDATE orders o
JOIN customers c ON o.customer_id = c.id
SET o.status = 'VIP'
WHERE c.country = 'DE';

Tip: Update-with-join syntax differs by DB: MySQL uses UPDATE a JOIN b ... SET ...; Postgres uses UPDATE a SET ... FROM b WHERE .... Know your dialect.

DELETE — remove old rows

EasyDML▼

📌 Revision keywords

  • In simple terms:
  • Soft delete often preferred in apps
  • FK constraints may block delete
DELETE FROM orders WHERE status = 'CANCELLED' AND created_at < '2024-01-01';

Tip: For very large deletes, loop in batches (DELETE ... LIMIT 10000) to avoid long locks, huge undo logs, and replication lag.

CREATE TABLE

EasyDDL▼

📌 Revision keywords

  • In simple terms:
  • DECIMAL for money, VARCHAR for text
  • Add PRIMARY KEY and needed indexes
CREATE TABLE employees (
  id INT PRIMARY KEY AUTO_INCREMENT,
  name VARCHAR(100) NOT NULL,
  dept VARCHAR(50),
  salary DECIMAL(10,2),
  hire_date DATE
);

Tip: Pick precise types, add NOT NULL + sensible defaults, define a primary key, and use utf8mb4. Constraints at the DB level are your last line of defense.

ALTER TABLE — add column

EasyDDL▼

📌 Revision keywords

  • In simple terms:
  • Can lock large tables — plan maintenance
  • Version with Flyway/Liquibase
ALTER TABLE employees ADD COLUMN email VARCHAR(150) AFTER name;

Tip: On large tables, ALTER may lock/rebuild — use online DDL (ALGORITHM=INPLACE) or tools like pt-online-schema-change/gh-ost.

ROW_NUMBER — rank employees by salary per dept

EasyWindow▼

📌 Revision keywords

  • In simple terms:
  • PARTITION BY dept ORDER BY salary
  • Keeps all rows unlike GROUP BY
SELECT name, dept, salary,
  ROW_NUMBER() OVER (PARTITION BY dept ORDER BY salary DESC) AS rn
FROM employees;

Tip: ROW_NUMBER() OVER (PARTITION BY g ORDER BY x) gives a unique rank per group — perfect for "top-N per group" or deduping (keep rn = 1).

RANK and DENSE_RANK

EasyWindow▼

📌 Revision keywords

  • In simple terms:
  • OVER (ORDER BY salary DESC)
  • Top-N per group pattern
SELECT name, salary,
  RANK() OVER (ORDER BY salary DESC) AS rnk,
  DENSE_RANK() OVER (ORDER BY salary DESC) AS drnk
FROM employees;

Tip: RANK leaves gaps after ties (1,1,3); DENSE_RANK doesn't (1,1,2); ROW_NUMBER is always unique. Pick based on how you want ties handled.

CTE (WITH clause)

EasyCTE▼

📌 Revision keywords

  • In simple terms:
  • WITH x AS (...) SELECT FROM x
  • Can be recursive for hierarchies
WITH dept_avg AS (
  SELECT dept, AVG(salary) AS avg_sal FROM employees GROUP BY dept
)
SELECT e.name, e.salary, d.avg_sal
FROM employees e
JOIN dept_avg d ON e.dept = d.dept
WHERE e.salary > d.avg_sal;

Tip: CTEs (WITH) make complex queries readable and can be referenced multiple times; a recursive CTE walks hierarchies/graphs (org charts, category trees).

Transaction — BEGIN, COMMIT, ROLLBACK

EasyTransaction▼

📌 Revision keywords

  • In simple terms:
  • SQL
  • ACID
  • ACID for money transfers
  • START TRANSACTION ... COMMIT/ROLLBACK
START TRANSACTION;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
-- On error: ROLLBACK;

Tip: Keep transactions short, do all reads/writes then commit fast, and always handle the error path with ROLLBACK. Choose the isolation level that's correct for the work.
