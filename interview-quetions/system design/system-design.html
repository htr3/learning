  4. Design: LB, app servers, DB, cache, queue, CDN

API Visualizer = operationalizing draw the hops — use in interviews to show end-to-end thinking.

A repeatable structure

  1. Clarify requirements + scope; state assumptions.
  2. Back-of-envelope estimates (QPS, storage, bandwidth).
  3. API design (endpoints/events).
  4. Data model + storage choice.
  5. High-level diagram, then deep-dive a component.
  6. Identify bottlenecks; scale & harden (cache, shard, queue, replicate).

Drive the conversation and call out trade-offs out loud — interviewers grade your reasoning, not a "right" answer.

How you architect software to meet functional needs at scale with acceptable latency, availability, and cost — not drawing boxes for fun.

Detailed explanation

  • They probe: trade-offs, failure modes, observability, data model
  • Not: memorizing every FAANG design — adapt to telco/BSS context

What they're really testing

Can you turn vague requirements into a system with explicit non-functional targets (scale, latency, availability) and defend trade-offs? Start every design by nailing those numbers — they drive every later decision.

Functional vs non-functional requirements?

Easy⭐ VIBasics▼

📌 Revision keywords

  • Functional:
  • Non-functional:
  • SQL

Functional: what the system does (generate report, provision SIM). Non-functional: how well (p99 < 2s, 99.9% uptime, 1M txn/day).

Examples from your work

  • Vodafone: functional = subscriber usage report; non-functional = SQL response time, batch window
  • Optima: functional = order to partner; non-functional = throughput, idempotency, audit trail

Why NFRs dominate

Functional = what it does (place order). Non-functional = how well (1M req/day, p99 < 200ms, 99.9% uptime, GDPR). The NFRs decide your architecture (cache? shard? async?), so quantify them up front.

CAP theorem and eventual consistency

MediumTheory▼

📌 Revision keywords

  • CAP
  • saga
  • ACID
  • Under network partition, choose Consistency (CP) or Availability (AP).
  • Most distributed systems are AP with eventual consistency.

Detailed explanation

Reporting tolerates seconds delay (eventual). Payment balance needs stronger consistency — leader DB or saga.

Follow-ups

BASE vs ACID? Basically Available, Soft state, Eventual consistency.

Go further with PACELC

During a partition choose C or A; else (normal operation) you still trade Latency vs Consistency. Practical: a bank balance leans CP, a product catalog/feed leans AP. Most "AP" systems are really tunable consistency (quorum reads/writes).

Vertical vs horizontal scalability?

EasyScale📊 Detailed diagram▼

📌 Revision keywords

  • Horizontal:

Vertical: bigger machine. Horizontal: more machines + load balancer. Cloud-native prefers horizontal with stateless app tier.

Vertical:  [App+DB on bigger VM]
Horizontal: [LB] --> [App1] [App2] [App3] --> shared DB / cache

Levers

Vertical (bigger box — simple, limited) vs horizontal (more boxes — needs statelessness + a load balancer). Keep services stateless (push session/state to Redis/DB), then add caching, read replicas, and sharding as load grows.

Back-of-envelope estimation (QPS, storage)

Medium⭐ VIEstimation▼

📌 Revision keywords

  • In simple terms:
  • Back-of-envelope estimation (QPS, storage)
  • DAU × actions/day ÷ 86400 ≈ avg QPS; peak ≈ 2–5× avg.
  • Storage = records/day × bytes × retention.

Example

1M txn/day → ~12 avg TPS, ~50 peak TPS (your Optima scale). Report 10M rows/day × 500B ≈ 5 GB/day raw.

The numbers to know

Estimate QPS = daily requests / 86,400 (≈10^5 s/day), then peak ≈ 2–3× average. Know rough latencies: memory ns, SSD µs, network within DC ms, cross-region ~100ms. Storage = rows × size × retention × replication factor. Round aggressively — they want the method.

Design idempotent HTTP APIs

Medium⭐ VIAPI📊 Detailed diagram▼

📌 Revision keywords

  • Idempotency-Key
  • idempotent
  • HTTP

Client sends Idempotency-Key; server stores key → response mapping; duplicate POST returns same result.

POST /activate  + Idempotency-Key: abc-123
  |-- first: process, store key, 201
  |-- retry: lookup key, return cached 201 (no double charge)

Pattern

Client sends an Idempotency-Key; server persists key→result behind a unique constraint and replays the stored result on retry. Critical because clients, gateways, and queues all retry (at-least-once).

Pagination and filtering at scale?

EasyAPI▼

📌 Revision keywords

  • In simple terms:
  • Pagination and filtering at scale
  • Cursor/keyset pagination for deep pages (not OFFSET on huge tables).
  • Filters indexed — align with DB composite indexes.

At scale

OFFSET pagination degrades on deep pages and can skip/duplicate rows under writes. Prefer keyset/cursor pagination (WHERE id > :cursor ORDER BY id LIMIT n) backed by an index.

HTTP status codes in API design?

EasyAPI▼

📌 Revision keywords

  • HTTP
  • API

200 OK, 201 Created, 202 Accepted (async), 400 client error, 401/403 auth, 404, 409 conflict, 429 rate limit, 503 downstream down.

Semantics matter

4xx = client must change the request (don't blindly retry); 5xx = server fault (safe to retry idempotent calls). Use 429 for rate limiting and 503 (+ Retry-After) when shedding load.

OpenAPI / API contracts between teams?

MediumAPI▼

📌 Revision keywords

  • API
  • CI

Single source of truth for request/response; generates clients; Pact or schema diff in CI catches breaking changes.

Contract-first

Define the OpenAPI spec first, generate server stubs + client SDKs, and gate CI on contract tests — producers and consumers evolve safely. This is exactly your MS-Builder / API-Visualizer angle.

Cache-aside flow

flowchart LR C[Client] --> A[App] A --> R{Redis?} R -->|hit| A R -->|miss| A A --> D[(MySQL)] A -->|fill| R

Problems

  • Thundering herd — mutex / single-flight
  • Penetration — bloom filter
  • Avalanche — TTL jitter

From your experience

Reference data in Camel routes — short TTL reduced partner call volume at Optima.

Strategies & pitfalls

SQL tuning for reporting (your Vodafone angle)

Medium⭐ VIDatabase📊 Detailed diagram▼

📌 Revision keywords

  • SQL
  • API
  • Spring
  • Boot

EXPLAIN plans, composite indexes matching WHERE/JOIN, avoid SELECT *, pre-aggregate heavy dashboards, partition by date.

Report API --> Query agg_daily_usage (indexed date, account_id)
              | miss index --> full scan (fix: composite index)
Heavy ad-hoc --> Read replica (not primary OLTP)

From your experience

Spring Boot reporting + MySQL: index + rewrite delivered >10% performance gains you can cite with numbers.

Order of attack

EXPLAIN → add the right index (composite, leftmost-prefix) → rewrite the query (avoid functions on indexed columns, N+1) → denormalize/pre-aggregate only if needed. Validate on prod-like data volume.

Database indexing strategies?

MediumDatabase▼

📌 Revision keywords

  • In simple terms:
  • Database indexing strategies

B-tree for equality/range; composite index column order = most selective first; covering indexes reduce table lookups.

Key rules

Composite index column order = equality before range, high selectivity first. A covering index (includes selected columns) avoids the table lookup. Each index speeds reads but taxes writes — don't over-index.

Primary-replica replication for read scale?

MediumDatabase📊 Detailed diagram▼

📌 Revision keywords

  • In simple terms:
  • Primary-replica replication for read scale

Writes to primary; reads to replicas; replication lag means eventual read consistency — route critical reads to primary if needed.

Write --> Primary MySQL --async binlog--> Replica1, Replica2
Analytics/report queries --> Replicas only

What it buys & costs

Primary-replica gives read scaling + failover, but introduces replication lag (replicas can be stale). Route critical read-your-writes to the primary; send heavy analytics to replicas. Sync replication = stronger consistency, higher latency.

Scale a relational DB — replication, sharding, partitioning

Hard⭐ VIDatabase📊 Detailed diagram▼

📌 Revision keywords

  • In simple terms:

Vertical scale first; read replicas for reporting; shard by tenant/region when write limit hit; partition large tables by date.

From your experience

Vodafone: indexes + query rewrite before shard complexity; read replica for Subscriber Tool lookups.

The ladder

Vertical → read replicas (read scaling) → caching → sharding (write scaling). Sharding is last because cross-shard queries/transactions get hard. Choosing a good partition key (even distribution, no hotspots) is the whole game.

Write-through vs write-behind caching?

MediumCache▼

📌 Revision keywords

  • Write-through:
  • Write-behind:

Write-through: update cache + DB together — consistent, slower writes. Write-behind: fast write to cache, async DB — risk on crash.

Trade-offs

Write-through (write cache+DB synchronously) keeps cache consistent but adds write latency; write-back (write cache, flush later) is fast but risks data loss on crash. Pick based on durability needs.

ACID vs BASE in distributed systems?

MediumDatabase▼

📌 Revision keywords

  • ACID
  • ACID on single-node RDBMS.
  • Microservices often BASE across services — compensate with sagas, idempotency, reconciliation jobs.

When each

ACID (RDBMS) for money/inventory where correctness is non-negotiable; BASE (eventually consistent, NoSQL) for feeds/analytics/high-scale where availability matters more. Many real systems mix both per data type.

Where does Kafka fit in system design?

Medium⭐ VIMessaging📊 Detailed diagram▼

📌 Revision keywords

  • Kafka
  • REST
  • Durable event log for async integration, audit trail, fan-out, decoupling peak load.
  • Not a replacement for every REST call.
Order Svc --publish OrderCreated--> Kafka Topic
   |--> Billing consumer
   |--> Notification consumer
   +--> Analytics sink

Why a log

Kafka decouples producers/consumers, buffers spikes, and—being a retained log—enables replay and adding new consumers later. It's the async backbone of event-driven designs and the natural place for an outbox relay to publish.

Message queue vs pub/sub topic?

EasyMessaging▼

📌 Revision keywords

  • Queue:
  • Topic:

Queue: one consumer per message (work distribution). Topic: many subscribers see same event.

Point-to-point vs pub-sub

A queue delivers each message to one consumer (work distribution); a topic fans out to many subscribers. Kafka does both via consumer groups (one group = queue semantics; multiple groups = pub-sub).

Why use async processing in system design?

EasyMessaging▼

📌 Revision keywords

  • API

Decouple peak load, improve API latency (202 + poll/webhook), survive downstream slowness with buffered queue.

What async gives you

Decoupling, spike absorption (buffer), independent scaling, and failure isolation (consumer down ≠ producer down). Cost: eventual consistency and harder debugging — add tracing + idempotency.

Message ordering guarantees in design?

MediumMessaging▼

📌 Revision keywords

  • In simple terms:
  • Message ordering guarantees in design

Partition by business key (accountId) so related events stay ordered; global order usually unnecessary and expensive.

How to guarantee order

Kafka orders only within a partition — route related events to the same partition via a key (e.g. accountId). Global ordering needs one partition (no parallelism), so order per-entity, not globally.

DLQ and retry in messaging design?

Medium⭐ VIMessaging📊 Detailed diagram▼

📌 Revision keywords

  • DLQ

Retry with exponential backoff; after N failures → DLQ for manual replay; never infinite retry blocking queue.

Consumer --> process fail --> retry topic (backoff)
                    | max retries --> DLQ --> ops replay tool

Resilient consumption

Retry transient failures with exponential backoff + jitter; after N attempts route to a DLQ, alert, and provide a replay tool. Make consumers idempotent so retries/duplicates are safe.

Design a rate limiter for public APIs

Hard⭐ VIAPI📊 Detailed diagram▼

📌 Revision keywords

  • API

Token bucket or sliding window in Redis; key = userId or API key; 429 + Retry-After.

Request --> Gateway --> Redis INCR key:apiKey:window
              | under limit --> forward to service
              | over limit  --> 429 Too Many Requests

Algorithms

Token bucket (allows bursts) and sliding window (smooth) are most common. For multiple instances, keep counters in Redis (shared state). Limit per API key/user/IP and return 429 with Retry-After.

Circuit breaker in system design?

Medium⭐ VIResilience▼

📌 Revision keywords

  • In simple terms:
  • Circuit breaker in system design

Stop calling failing downstream; fail fast; half-open probe after cooldown — protects thread pools at 1M txn/day.

States

closed → open (fail fast past an error threshold) → half-open (trial requests). Prevents cascading failures and gives a struggling dependency time to recover. Pair with timeout + fallback.

Graceful degradation under load?

MediumResilience▼

📌 Revision keywords

  • In simple terms:
  • Graceful degradation under load

Drop non-critical features (recommendations) before core (order submit); queue or return cached stale data with disclaimer.

Degrade, don't fail

Return cached/last-known or default data, drop non-essential features (feature flags), and protect the core path. A partial response beats a 500 — design which features are sheddable up front.

HardClassic📊 Detailed diagram▼

📌 Revision keywords

  • In simple terms:
  • Design a distributed cache (Redis cluster)

Consistent hashing across shards; replication for HA; TTL per key; cache-aside at app.

Core ideas

Consistent hashing to spread keys and minimize reshuffling when nodes change, an eviction policy (LRU/LFU + TTL), and replication for availability. Decide consistency (write-through vs invalidate) and handle hot keys.

CDC or events from OLTP → search index; query service hits ES; eventual consistency acceptable.

MySQL --binlog/CDC--> Indexer --> Elasticsearch
User search --> Search API --> ES (not OLTP for full-text)

Building blocks

An inverted index (term → doc list), built by an async indexing pipeline, served by Elasticsearch/OpenSearch with ranking (TF-IDF/BM25). Keep the search store separate from the source-of-truth DB and update it via events.
