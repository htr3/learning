Explain the test pyramid

EasyBasics▼

📌 Revision keywords

  • REST
  • Mockito
  • API
  • TestNG

Many fast unit tests, fewer integration tests, fewest E2E/UI — balance speed, cost, confidence.

Detailed explanation

Anti-pattern: ice-cream cone (mostly manual/E2E). For REST services: unit (Mockito) + API integration (MockMvc/TestRestTemplate) + selective E2E in staging.

From your experience

Vodafone: grew unit + API tests with TestNG to hit 90% coverage on critical paths without slowing every commit.

Why the shape

Many fast unit tests at the base, fewer integration/slice tests in the middle, very few slow E2E tests at the top. Inverting it (the "ice-cream cone") gives slow, flaky suites. In Spring: @WebMvcTest/@DataJpaTest slices sit in the middle, @SpringBootTest + Testcontainers at the top.

JUnit vs TestNG — differences you used

EasyFramework▼

📌 Revision keywords

  • JUnit
  • TestNG
  • XML
  • Spring
  • Boot
  • TestNG: test groups, parallel suites, flexible XML suites, dependencies between tests.
  • JUnit 5: modern extensions, widespread in Spring Boot greenfield.

Example

@Test(groups = {"smoke", "reporting"})
public void shouldReturnReport() { ... }

From your experience

Vodafone stack standardized on TestNG — know both for interviews; Spring Boot docs often show JUnit 5.

Practical differences

TestNG has built-in data providers, flexible suite/groups config (XML), and parallel execution; JUnit 5 caught up with @ParameterizedTest, tags, and extensions. Both integrate with Mockito/Spring — the concepts transfer, so emphasize what you tested, not which runner.

How do you use Mockito effectively?

Medium⭐ VIUnit▼

📌 Revision keywords

  • Spy
  • ArgumentCaptor
  • Mockito
  • Mock dependencies, assert interactions and return values.
  • Prefer testing behavior not implementation — avoid over-verifying internal calls.

Example

@Mock ReportRepository repo;
@InjectMocks ReportService service;

@Test
void returnsDto() {
  when(repo.find("id")).thenReturn(entity);
  assertThat(service.fetch("id").getTotal()).isEqualTo(100);
  verify(repo).find("id");
}

Follow-ups

@Spy partial mock; ArgumentCaptor for complex payloads; static mocks (Mockito 3.4+) sparingly.

Do & don't

  • when(...).thenReturn(...) to stub, verify(...) for important interactions — don't over-verify internals (brittle).
  • Use @Mock/@InjectMocks; prefer constructor injection so mocks slot in cleanly.
  • Mock your collaborators, not value objects or the class under test.

Integration testing REST APIs (Spring + TestNG)

Medium⭐ VIIntegration▼

📌 Revision keywords

  • SpringBootTest
  • MockMvc
  • TestRestTemplate
  • Transactional
  • REST
  • Spring
  • TestNG
  • api

@SpringBootTest + MockMvc or TestRestTemplate; test DB via Testcontainers or embedded H2 with caution.

Example

mockMvc.perform(get("/api/v1/reports/1"))
  .andExpect(status().isOk())
  .andExpect(jsonPath("$.accountId").value("DE123"));

Detailed explanation

Test happy path + 400 validation + 404 + 500 mapping. Use test data builders; rollback DB per test with @Transactional on test class.

From your experience

Critical Vodafone reporting endpoints had integration tests before release — caught contract breaks when SQL columns changed.

How to do it well

@SpringBootTest(webEnvironment=RANDOM_PORT) + TestRestTemplate/WebTestClient against a real DB via Testcontainers (not H2 — it hides dialect bugs). Test the full request→DB→response, including validation and error mappings.

Code coverage — JaCoCo and what it does NOT tell you

MediumMetrics▼

📌 Revision keywords

  • In simple terms:
  • Coverage = lines/branches executed by tests.
  • High coverage ≠ good tests — can miss assertions and edge cases.

Detailed explanation

Gate at 80–90% on critical modules; exclude generated code. Pair with review of test quality and prod incident history.

From your experience

60→90% initiative included branch coverage on payment filters and date boundary reports.

What it misses

Coverage shows lines executed, not asserted — you can have 90% coverage with weak assertions. It says nothing about edge cases, concurrency, or correctness. Use it as a floor/guardrail, not a goal; pair with mutation testing (PIT) for assertion quality.

Do you practice TDD? When is it worth it?

EasyProcess▼

📌 Revision keywords

  • API
  • Red-green-refactor: write failing test, minimal code, refactor.
  • Best for pure logic; less strict for exploratory spikes — add tests before merge.

From your experience

Pragmatic: test-first for bug fixes (reproduce with test) and new API contracts; retro tests when inheriting legacy Vodafone modules.

When it pays

Red → green → refactor. TDD shines for well-specified logic (parsers, calculations, bug fixes — write a failing test that reproduces it first). It's less natural for exploratory UI/spike work. Even when not strict TDD, write the test close to the code.

Detailed explanation

Follow-ups

vs E2E? Contracts faster; E2E still needed for few golden paths.

The value

Tools like Pact let the consumer publish expectations and the provider verify them in CI — catching breaking API changes before deploy without standing up the whole system. Far faster and less flaky than end-to-end tests for inter-service contracts.

Performance testing workflows (Camunda / XL Axiata)

MediumPerf▼

📌 Revision keywords

  • API
  • SQL

Load test BPMN paths with realistic concurrency; monitor engine DB growth, job executor lag, external task timeouts.

From your experience

Optimized Camunda workflows and test framework — ~5% faster perf test execution, better reliability before prod.

Follow-ups

Bottleneck in engine vs external API? Profile SQL on ACT_RU_* tables, tune async continuations.

Approach

Define the SLA (throughput, p95), generate realistic load (JMeter/Gatling), and watch the right signals: latency percentiles, error rate, DB/connection-pool saturation, and queue/process-instance backlog. Test on prod-like data volume and find the bottleneck before tuning.
